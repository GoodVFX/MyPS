# 晚间总结

你正在执行晚间总结任务。这是每天最重要的 Skill——它不仅总结今天，还负责惊奇度扫描和情绪教练调用。以下是完整的输出规则。

---

## 处理流程

### 步骤 0（先决条件）：确认数据目录路径

Cron 启动时工作目录不一定是 `~/.hermes/`。所有 `data/` 路径均相对于 `~/.hermes/`，所以第一步必须是：

```
检查 ~/.hermes/data/ 是否存在
   ├── 存在 → 以 ~/.hermes/ 为 base 路径
   ├── 不存在 → 用 search_files 或 find 定位 data/ 实际位置
   └── 找不到 → 输出 [SILENT] 并结束（但记录日志供排查）
```

**常见错误**：Cron 未设 workdir 时从 `~/` 启动，`data/diary/` 解析为 `~/data/diary/` 即文件不存在。修复：Cron 创建时设 `workdir='~/.hermes'`。

**调试技巧**：如果所有数据文件都找不到，用 `session_search` 查一下之前的 Cron 运行记录——可能上轮也失败了，或者数据本身确实不存在。不要假设「有数据但没找到」vs「本来就无数据」——主动确认。

**路径注意**：`memory/` 目录位于 `~/.hermes/memory/`，与 `data/` 平级，不在 `data/` 下。步骤 0.6 中读取的 `memory/mood-trends.md` 对应 `~/.hermes/memory/mood-trends.md`（而非 `~/.hermes/data/memory/mood-trends.md`）。

### 步骤 0.5：检查是否为重跑（失败重跑或清洁重跑）

Cron 可能因两种原因重跑：
- **失败重跑**：网络波动/临时故障失败后，调度器自动重试
- **清洁重跑**：前一轮成功运行（last_status=ok, last_delivery_error=null），但用户/系统触发了再次执行

两种重跑都应当正常输出，但处理方式有细微差别。

1. **确认前一轮的状态**：检查当前 cron job 的 output 目录下今天的最新文件。

   **方法 A（推荐）**——已知 job ID 时直接用：
   ```bash
   ls -lt ~/.hermes/cron/output/<your-job-id>/ | head -5
   ```

   **⚠️ 输出文件命名陷阱（2026-09-01 实测）**：cron output 文件名为 `YYYY-MM-DD_HH-MM-SS.md`（带时分秒），**不是** `{date}.md`。用 `os.path.exists(f"{out}/{today}.md")` 判断「今日是否已运行」会误报 false——实测简报 08:38 已正常执行，但 `2026-09-01.md` 不存在，实际文件是 `2026-09-01_08-38-07.md`，一度误判「简报可能失败」。正确姿势：`ls -lt` 目录取最新文件，或 glob 匹配 `{today}*` 前缀再读。

   **方法 B（推荐）**——读取 cron 配置来查找 job ID：

   方式 a（execute_code，优先——JSON 解析比 shell grep 更可靠）：
   ```python
   import json, os
   with open(os.path.expanduser("~/.hermes/cron/jobs.json")) as f:
       jobs = json.load(f).get("jobs", [])
   for j in jobs:
       if j.get("name") == "daily-review":
           print(j["id"])
           break
   ```

   方式 b（shell 兜底——注意只查 jobs.json，不要 cat *.json，backup-status.json 会混入）：
   ```bash
   cat ~/.hermes/cron/jobs.json | grep -B5 '"name": "daily-review"'
   ```
   从输出中提取该 job 的 `"id"` 字段，然后直接检查该目录：
   ```bash
   ls -lt ~/.hermes/cron/output/<找到的job-id>/ | head -5
   ```

   **方法 C（兜底）**——当 cron 配置也找不到时，通过目录特征推测：
   ```bash
   # 列出所有 job 目录，按修改时间排序，找到今天最新运行的那个
   ls -lt ~/.hermes/cron/output/ | head -10
   ```
   daily-review 任务的特征：目录下有大量历史文件（每天一个），最近修改的就是本轮或上一轮的输出。

   **判断「首次运行」**：如果 output 目录下最新的文件日期是**昨天或更早**，说明今天是第一次执行（不是重跑）——此时不需要任何重跑处理，直接走正常流程。只有在今天已存在输出文件时才需要判断是失败重跑还是清洁重跑。**不要因为「今天是第一次跑」而跳过步骤 0.6 等后续检查**——首次运行和重跑都要完整执行全部流程（2026-08-02 实测：输出目录最新文件为昨日 → 判定首次运行，正常走零录入日流程）。

2. **确认 mood-trends 是否已有今日条目**：读取 `~/.hermes/memory/mood-trends.md`，搜索 `### YYYY-MM-DD 情绪评估`（替换为今日日期）。
   - **存在** → 清洁重跑（前一轮已成功写入情绪评估）。后续 emotion-coach 调用时**跳过步骤 4（写入 mood-trends.md）**，避免重复条目
   - **不存在** → 首次运行或失败重跑。正常执行全部流程。

3. **输出标记**：
   - **失败重跑**：输出末尾加一行说明——`补充说明：刚才那轮因 [原因] 没跑成，现在补上了。`
   - **清洁重跑（mood-trends 已有今日条目）**：无需额外说明。直接正常输出。
   - **清洁重跑（检查确认前一轮成功但 mood-trends 无条目——异常情况）**：正常执行全部流程，包括 emotion-coach 写入，无需特殊说明。

4. **不要因为重跑而静默**：只要本轮成功就正常输出。用户有数据需要回顾，前一轮失败不是跳过总结的理由。

#### 新增场景：输出文件存在但 mood-trends 无今日条目（静默写失败）

2026-07-01 触发了此场景：daily-review 正常跑完并推送了总结（含月度总结），但 action=patch 写入 mood-trends.md 时未实际写入（patch 成功但目标位置不对）。这导致情绪趋势文件出现日期断层，但系统无任何报错。

**检测方法**（在步骤 0.5 中同步执行）：
1. 检查 `~/.hermes/cron/output/<job-id>/` 下今日有无输出文件
2. 若有输出文件（说明 job 跑了），但 mood-trends 无今日条目 → 可能发生了静默写入失败

**处理方式**：
- 不重复写入缺失的 mood-trends 条目（缺乏当日碎碎念上下文，生成的评估空洞）
- 在晚间总结的善意提醒区块中加一句话说明：`💡 补充：昨晚的总结因系统原因未在情绪趋势中留下记录，但内容已正常推送。`
- 正常执行本轮全部流程（包括 emotion-coach 写入今日条目）

**预防措施**：在 emotion-coach 步骤 4 写入后，加一行验证代码：
```python
# 写入后立即验证
check = read_file("~/.hermes/memory/mood-trends.md")
if f"### {today} 情绪评估" not in check.get("content", ""):
    # 写入失败，重试一次
    ...重试逻辑
```

### 步骤 0.6：检查前序日期是否有遗漏

前一天的 Cron 可能因系统宕机、网络故障或调度器错过时间窗口而完全未执行。这会导致数据文件出现了日期断层，但不会触发步骤 0.5 的重跑检测（因为作业本身没有失败，只是从未运行）。

**⚠️ 输出文件存在 ≠ 已推送（2026-08-05 实测）**：判断前一日是否真正完成前，交叉验证三处，不能只看 output 目录有文件：
1. output 文件尾部是否有 `## Error` 区块——失败运行（如 `peer closed connection`）同样会留下大体积输出文件（含完整 skill 全文 + Error 段）
2. jobs.json 中该 job 的 `last_status` / `last_delivery_error`——运行成功但推送失败（如 Weixin `rate limited`）时用户实际未收到
3. mood-trends.md 是否有该日条目——这是最终判定依据

三者一致确认缺失后，按下方「遗漏日处理」说明。若早间简报已提过前日失败（简报会引用 last_delivery_error），晚间补充区块引用简报结论即可，不要重复描述故障细节。

**执行失败不经简报（2026-09-14 实测）**：9/13 cron 超时失败（last_status=error、last_delivery_error=None），次日简报照常送达且只字未提——简报引用的是 delivery error，执行失败不在其视野，不能假设「简报已经说过了」。三连验证确认缺失后，由晚间总结的善意提醒自行补一句：缺失事实 + 关键内容无实际遗漏的结论（如「22:04 到郑、dl-026 已标完结，事实都在档案里」），一行即可。

**简报与昨日总结双双推送失败（2026-08-24 实测）**：连续 Weixin 限流时（昨日 daily-review 22:08 推送失败 + 今早简报 08:40 推送失败），「引用简报结论」路径不可用——简报本身没送达，其输出文件中也不会引用前日失败。处理：自行交叉验证（output 文件有 Response + mood-trends 有该日条目 + jobs.json last_delivery_error 三者）确认「运行成功、仅推送失败」，然后合并为一句说明——注明两份内容里的关键提醒（如截止提醒、定时提醒）是否已被独立 Cron 覆盖、有无实际遗漏。不分别罗列两次故障细节，不重复已单独提醒过的内容。

**变体——仅简报失败、昨日总结正常（2026-08-30 实测）**：Weixin 限流只打在简报上（jobs.json：daily-review last_delivery_error=None、daily-briefing 有值）。处理相同：交叉验证（简报 output 文件有 Response 段但 last_delivery_error 报限流 → 运行成功、仅推送失败）后合并为一句说明，并核对简报关键提醒（如明日到期的 deadline）是否已有独立 reminder cron 覆盖——验证三连判据：jobs.json 中该 reminder job 存在 + last_status=None + output 目录不存在 = 未到触发时间、属预期（明早会到，无遗漏）。不需要补推简报全文，晚间总结的到期待办区块已覆盖其关键内容。
**变体——仅简报失败、昨日总结正常（2026-09-03 复现，补充 8/30 盲区）**：8/30 变体第二次出现（当日简报 bccc5ba95b30 08:32 运行成功、推送被微信限流；jobs.json：daily-review err=None、briefing 有值），处理同上。本次暴露 8/30 未覆盖的盲区：**简报里的非 deadline 内容，晚间总结不会自动覆盖**——反复问而用户未答的定调问题（「三个资料项目继续推还是放一放」）、本周末将到的家修提醒（「空调管周六 9/5」）、待跟进建议（「电车方向盘问一嘴」）。这类内容只存在于简报、用户又没收到时，在 顺便说一句 各带一行补上。做法：简报 Response 段内容与当晚总结将输出的区块做一次清单差集——差出来的非 deadline 项才补带；deadline 项由到期待办区覆盖，不重复。

**正常送达场景——简报点名行动项的完成追踪（2026-09-07 实测）**：简报正常送达（无推送失败）时，它点名的「今日行动项」（如「宁德发票交财务」）在晚间总结时对照 diary/events/todos 查完成信号：有 → 并入今日完成区一起报（如 qt-023 续签闭环连带 dl-035 批量 6/6 齐活）；无 → 顺便说一句 给一行轻跟进（「交了当我没说，没交明天记得带」），不展开成完整提醒、不质问。同一原则适用简报当天的征询性问题（如「三个资料项目推不推」）：早上刚问过未答，晚间不重复追问——同一天两次是噪音，留给下一天简报自然跟进。**反向情形同样成立（2026-09-08 实测）**：征询性问题当天被用户在 diary/events 里给了答案（「属于长期项目，有空补充即可」）→ 在今日完成区记一笔闭环（「简报早上问的，今天给了话」），不再当悬置问题；简报点名的收尾项当天完结的（如小电电方向盘 dl-029 确认完结）同样并入今日完成区报闭环，不重复展开。**变体——响应中、无完成确认（2026-09-22 实测）**：行动项当日有响应但晚间时点未完结（如傍晚计划取消后又恢复、定当晚执行，结果无落盘）→ 记入今日完成区标「响应」而非「闭环」，带一句确认钩子（「去了/办了明早说一声就闭环」），把结果确认留给次日简报；既不当完成报，也不走未响应跟进。

**承接前晚的确认钩子——次日闭环（2026-09-23 实测）**：前晚标「响应、待确认」的行动项（如 dl-048「看三哥」前晚定了当晚去、带钩子「去了明早说一声就闭环」），次日的 diary/events 出现完成陈述（实测 9/23 日记「昨晚去看三哥，回来有点感冒」）→ 按「Cron 环境下的待办状态同步」主动标 done，在今日完成区报闭环（「昨晚已成行，今天确认闭环」）。两个要点：①**done_at 用事件发生日，不用确认日**（9/22 晚去的就写 2026-09-22，不写 9/23）——否则会污染「到期日≠完成日」以外的另一维统计；②同一件事不要既在 9/22 报「响应」又在 9/23 重新论证一遍，后者一句话闭环即可。若简报当天还留着未销的旧口径（如 9/23 简报写「昨晚决定去，还没销」），闭环记录顺带把这条口子合上。

**变体——无显式完成陈述的日程类闭环（2026-09-26 实测）**：简报点名待确认的日程类待办（如「中秋值班还挂着未确认，值完说一声我关掉」），用户当天未正面回复、只报了「今明两天休息」时，不必把确认悬到下一轮。满足以下三条即可主动关闭：①前一晚的会话证据已记载事件当日实际发生（如 9/25 mood 备注的「日班值守、午后主战场在 测试硬件N」——dl-046 值班的核心动词「值守」有明确记载）；②日期窗口已过；③用户次日申报进入休息/新阶段，间接确认本周已收尾。done_at 用事件发生日（沿用 9/23 dl-048 先例），输出里一句闭环带过（「昨晚值班日在案，已按 9/25 完成标注并关掉，明早简报不会再问」），当场终止「简报每天重复问」的循环——日程类待办拖成未确认循环是噪音源，自主收口优先于等确认。区别于 dl-014 出勤类判据（需用户原话完成陈述）：日程类待办的事件本身有客观窗口，窗口+旁证即足够。

**变体——仅昨日总结推送失败、简报正常（2026-08-31 实测）**：与 8/30 实测互为镜像——Weixin 限流打在昨晚的 daily-review 上（jobs.json：daily-review last_delivery_error 有值、daily-briefing err=None）。**错误归属陷阱**：22:00 运行时 jobs.json 里的 last_delivery_error 属于**上一轮**（昨晚那轮），因为本轮尚未完成——看到 error 别当成「本轮之前失败了」，而是「昨晚的总结没送到」。交叉验证三连（昨晚 output 文件存在且有 Response 段 + mood-trends 有昨日条目 + last_delivery_error 报限流）确认「运行成功、仅推送失败」。处理：核对昨晚总结的关键提醒是否已被独立 reminder cron 覆盖——本例 dl-008（填报截止 8/31）与 dl-031（徐老师会面）均有今早独立提醒（07:30/08:00，output 目录存在 = 已触发），无实际遗漏 → 在「顺便说一句」区块合并为一句说明（如「昨晚的总结跑完了，但推送被微信限流没送到。没有实际遗漏的提醒——填报截止和会面，今早都由独立提醒补上了」），不补推全文、不罗列昨晚总结的内容。

**变体——用户已在会话中自行排查并决定维持现状（2026-09-01 实测）**：早间简报 + 每小时监控双双被微信限流吞掉，但用户 08:45 主动发起排查会话、简报已在会话中补发，并明确决定「先保持吧，限速吞了就补发」（不迁移企业微信）。处理：晚间总结只一句带过（或并入其他系统说明），不再报 delivery error 本身；同一 job 的重复限流在用户接受的前提下属预期噪音，高频 job（每小时监控）的 last_delivery_error 也一并忽略，不每晚罗列。

**例外——整份晚间总结未送达仍需一行**：用户「吞了就补发」的容忍决定针对简报/监控级噪音，不覆盖整份晚间总结缺失——用户可能正因缺失发起状态查询（2026-09-02 实测：次日会话以「现在是什么状态？」开头，当晚总结缺失是合理诱因）。判定昨晚总结确实未送达（output 有完整 Response + mood-trends 有昨日条目 + last_delivery_error 报限流，三连验证）后，每次仍给一行说明：缺失事实 + 无实际遗漏的核验结论（关键提醒是否已由独立 cron 或用户当日会话闭环），不因用户已接受限流而省略、也不展开故障细节。判断用户是否已知情：session_search 摘要中出现用户主动发起的排查会话即为已知情。

**已补发场景的承接（2026-09-20 实测）**：若次日晨 fragment-catcher 已把「推送失败 + 当日补发原文」作为事件记入 data/events/（实测 08:27 条目），晚间总结不必再单独开说明行——在 📰 今日事件区块照常列出该条并带半句核验结论（如「原文已补发，无遗漏内容——这条线闭环」）即可。不重复故障细节、不再占用善意提醒区。

**检查方法**：

1. 读取 `~/.hermes/memory/mood-trends.md`，用正则提取所有 `### YYYY-MM-DD 情绪评估` 标题中的日期
2. 按日期排序（注意：文件中的条目不一定是按日期顺序的——写失败、重跑等情况会导致日期断层），取最近的日期
3. 与今日日期对比，如果存在中间缺失的日期 → 说明遗漏了

   示例代码：
   ```python
   import re, os
   content = open(os.path.expanduser("~/.hermes/memory/mood-trends.md")).read()
   dates = re.findall(r"### (\d{4}-\d{2}-\d{2}) 情绪评估", content)
   dates.sort()
   last_date = dates[-1] if dates else None
   # 然后对比 last_date 和 today，看中间是否有缺失
   ```

**遗漏日处理**：
- **先查历史再输出**：缺失日若已在更早的晚间总结或早间简报中说明过（读取近期 daily-review 输出文件的 Response 段确认），本轮不重复提及，只处理新发现的缺失（2026-08-09 实测：8/4、8/6 两处缺口已分别被 8/5、8/7 的总结说明过，本轮直接跳过，避免重复噪音）
- 如果仅缺失 1 天 → 在晚间总结中的善意提醒区块加一句话说明。不需要补跑整个总结，但要让用户知道系统意识到有缺失。
  ```
  💡 补充：昨晚的总结因系统宕机没跑成。今天正常回顾。
  ```
- 如果缺失 2 天及以上 → 在善意提醒区块中概述缺失天数，并询问是否需要手动补推关键信息（待办到期、积压提醒等）。
- 如果 mood-trends.md 尚未初始化或不存在 → 跳过此步骤（首次使用无历史数据）。

**不修改数据结构**：只做观察和输出，不要回填 mood-trends.md 中缺失日期的条目（除非下一轮 daily-review 的正常流程触发了写入）。缺失的总结因为缺乏原始数据（用户当天的碎碎念），生成的评估也是空洞的。

### 数据完整性检查（Step 1 子节点 — 新增）

**问题场景**：用户当天有活跃会话（通过 `session_search` 可确认），但 data/ 下的 diary/ideas/events/knowledge 文件不存在或无内容。这表示碎片捕获阶段的持久化写入失败（文件未落盘），但会话记录中保留了完整内容。

**检测方法**（在 Step 1 采集完数据文件后执行）：

1. 确认数据文件为空或不存在 → 调用 `session_search(query="YYYY-MM-DD")` 检查当日是否有活跃会话
2. 若 session_search 返回有内容的摘要，但数据文件为空 → 标记为「数据持久化异常」
   - 排除误判：如果 session 摘要明确说「文件不存在」或「无法写入」→ 确认是已知问题，不是新异常
   - 排除误判（2026-08-21 实测）：会话内容若只是「修正昨日记录 + 系统故障排查」（如纠正昨日文件中的工具名称、诊断 cron 失败、手动补推简报），不产生任何今日碎片 → **不是持久化异常**。修正操作落在昨日文件（patch 前日 diary/events），排查会话本就不产出碎片。判断标准：会话中有无「用户口述的新内容」（事件/想法/知识/待办）——没有 → 正常零录入日，不标记异常，直接走零录入日输出格式
   - 排除误判（2026-08-27 实测）：**执行/安装型长工作会话**（如全天 测试硬件N 装机，286 条消息，agent 终端操作为主）只落盘 2 条里程碑碎片（开工、完成）属正常，不是持久化异常。判定依据是「用户口述的新内容」是否落盘，不是消息条数——大量消息是 agent 执行终端命令，不产出碎片。里程碑碎片已入 diary/events 即视为完整捕获，无需标记异常。
   - 排除误判（2026-08-29 实测）：**编译/整理型会话**（用户请助手把已有材料整理成文档，如「把 8/28 两次测试结果总结成报告交 GPT 审阅」）——产出物是 knowledge/ 下的新建独立文档，无 diary/events 碎片属正常：既不是持久化异常（交付物已落盘，方法 B 可捕获），也不按零录入日处理。知识汇报按「今日新建知识文档」计，输出用零录入日紧凑格式即可。
   - 排除误判（2026-09-05 实测）：**自我实验/讨论型会话**（对 MyPS 自身运行时做实验探讨——休息日 10:42 会话从「今天休息」转入 GLM↔DeepSeek 后台模型切换实验，agent 大量终端检查 + 概念讨论，无闭环里程碑、等用户发 API key 继续）不落盘任何碎片属正常，不标记异常。处理模板：零录入日紧凑格式输出；开场句叙述会话（见下方开场句规则）；补充区块带一句「实验闭环后值得给概念文档补一节实测记录」式的延后入库提议（实验卡在外部输入时，认知结论先留在会话里、闭环再入库是预期节奏，不是丢失）。
   - 排除误判（2026-09-25 实测）：**里程碑产出会话——产出全落知识文档/归档 + 待办闭环，diary/ideas/events 全缺**（实测：12:12-18:00 测试硬件N 测试大会话 224 条消息，产出 4 篇新建知识文档 + 1 篇更新 + 2 份 documents/ 原文归档 + dl-044 完结，三个碎片文件全缺）。不是持久化异常（产出物全部落盘），也不是零录入日（有知识新增 + 待办完成）——按标准 emoji 区块格式输出：📖 日记区块跳过，开场句点明「今天的记录不在日记里，在 N 份文档里」，知识区块成为当日主体，待办完成区报闭环。
3. 将异常信息加入最终输出，在善意提醒区块中以自然语气说明

**输出示例**（融入善意提醒）：
```
💡 你 10:02 会话中的几条记录（日记、灵感、知识碎片）因系统持久化异常没有写入数据文件，
  只在会话记录里。有时间的话可以补充录入——特别是 [关键内容简述]。
```

**原因分析**：碎片捕获阶段（用户发送消息 → fragment-catcher 处理 → write_file）中，file write 步骤可能因路径解析失败、工具调用超时或被后续操作覆盖而未实际落盘。此检查确保即便写入失败，用户的关键内容仍能被晚间总结识别和提及。

**变体——patch 中断致文件清零（2026-10-01 实测）**：posts-log.md 被一次中断的 patch 清成 0 字节——不是「未写入」而是「已有内容被清」，与前述静默写失败是两种故障。检测：扫描时文件存在但 0 字节、或行数较近期认知骤降即可疑。重建路径：当天会话记录里含 patch 前全文时，依会话全文重写并逐行核对（实测 174 行重建无失），diary/events 通常已留事故与重建记录（⚠️ 标记行），照抄即可。预防：大文件 patch 前先 cp 快照，patch 后立即验行数/尾部内容。汇报按「今日完成」闭环报（事故+重建一句话），不当系统故障展开。

**预防措施**：
- 每日回顾结束时验证关键数据文件是否存在（diary/YYYY-MM-DD.md, events/YYYY-MM-DD.md）
- 若 session_search 显示有内容但文件缺失 → 在输出中引导用户补充录入

### 数据采集实用方法（Step 1 子节点）

以下方法在 Cron 环境中已验证可用：

**quotes.md 今日新增**
```
search_files(pattern="YYYY-MM-DD |", path="~/.hermes/data/quotes/quotes.md")
```
搜索到的匹配行即为今日新增好句。无匹配则无新增。

**知识主题今日新增**（三种检测方法，按优先级使用）

**方法 A（碎片格式检测——推荐）**：读取 knowledge/ 下各主题文件，在「碎片积累」区块中搜索 `YYYY-MM-DD` 日期模式来确认今日新增条目数。

**方法 B（文件修改时间检测）**：`ls -la --time-style=+%Y-%m-%d` 检查修改日期，今日修改的再读内容确认。

**方法 C（独立新文档检测——新增 2026-07-16）**：某些知识以整篇文档而非碎片条目的形式存储（如竞品分析、架构草案、工作流方案），这些文档不带 `## 碎片积累` 区块，也没有 `- YYYY-MM-DD |` 日期前缀行。检测方法：
1. 列出 knowledge/ 下所有 `.md` 文件，排除 `_` 前缀的模板
2. 对每个文件，检查是否包含今日日期（YYYY-MM-DD）关键词但在文件开头 500 字符内无 `## 碎片积累` 区块
3. 同时交叉引用当日 diary/ 和 events/ 文件中出现的「存到knowledge」「已存knowledge」「已入库」「知识」等模式，提取文件路径
4. 这些文档计入「主题数」而非「碎片条数」——在知识积累汇报中以独立文档形式呈现

示例检测代码：
```python
import os, re, glob
from datetime import datetime
today = datetime.now().strftime("%Y-%m-%d")
base = os.path.expanduser("~/.hermes")

# 检测新创建的独立文档
standalone = []
for f in glob.glob(f"{base}/data/knowledge/*.md"):
    fname = os.path.basename(f)
    if fname.startswith("_"):
        continue
    content = open(f).read()
    has_fragments = "## 碎片积累" in content
    mentions_today = re.search(rf"{re.escape(today)}", content[:500])
    if mentions_today and not has_fragments:
        standalone.append(fname)

# 从日记中提取\"存到knowledge\"的引用
diary_path = f\"{base}/data/diary/{today}.md\"
if os.path.exists(diary_path):
    diary = open(diary_path).read()
    saves = re.findall(r\"(已?存(?:入|到|在)? ?knowledge/[^\\s)]+)\", diary)
    for s in saves:
        fname = s.split(\"/\")[-1].replace(\".md\",\"\").strip()
        if f\"{fname}.md\" not in standalone:
            standalone.append(f\"{fname}.md\")

print(f\"Standalone new documents: {standalone}\")
```

**方法 C 盲区——短格式日期引用 + 更新文档误判（2026-08-24 实测）**：方法 C 正则要求完整 `YYYY-MM-DD`，但新文档可能在首 500 字符内只用短格式引用当日（实测 `家庭-孩子研究生.md` 内容为「（8/24 用户存入银行并转给家人）」——`M/D` 无年份，A/C/E 全部漏检，仅靠方法 B（`ls -lt` knowledge 目录 mtime）交叉检查发现）。教训：**方法 B 应每日必跑，不是可选项**——A/C/E 零命中 ≠ 今日无新增，`ls -lt` 出现今日修改但未被任何方法捕获的文件，必须 read_file 确认。**A/B 裁决顺序（2026-09-17 实测）**：B 命中而 A 计零时，先怀疑自己扫描脚本的正则、再怀疑数据——常见坑是从本 skill 示例向 execute_code 转录代码时丢掉 `- ` 后的空格（`^-{today}` 永远匹配不到 `- {today}`，当日碎片全部静默漏计），read_file 直读裁决后修正正则重扫，不要直接按「无新增」输出。另外方法 C 命中的不一定是「新建」文档——也可能是既有文档的当日更新（实测 `健康档案.md` 今日追加就医+用药记录，被方法 C 捕获但实为更新）。汇报时先读文件开头区分「新建」与「更新」，新建列入「今日新建知识文档」，更新并入「更新」表述，避免误报。第三种盲区（2026-08-26 实测）：新建文档的头部可能引用**未来执行日期**（如 `> 执行日期：2026-08-27`），不含今日日期，A/C/E 的日期正则全部失效——只能靠方法 B 捕获。实测 `projectx-n305-reinstall-btrfs.md` 今日创建但头部标注明日执行，方法 B 命中、read_file 确认后按「今日新建知识文档」汇报（不按碎片条数），即使文档内没有任何今日日期痕迹。
**变体——方法 B 命中但全文零今日痕迹（2026-09-07 实测）**：文件 mtime 为今日、但全文（含头部与尾部）无任何今日日期、内容全标昨日或更早——可能是对昨日文档的无标注追加/编辑。read_file 看不出改了什么时，用 session_search 归因修改原因：实测 `deepseek-API-定价.md` mtime 今日 11:44、全文日期全为 9/6，会话摘要确认是当天上午把「9/6 结算 ¥7.43 归因」追加进了用量分析区。归「今日更新」汇报（不按碎片条数、不算新建），知识区用一行带过即可。

**方法 C 盲区——带「碎片积累」标题的新建概念文档被误判为「更新」（2026-09-04 实测）**：方法 C 的前提「独立文档不带 `## 碎片积累` 区块」并非恒真——新建文档可自带「碎片积累（核心概念链）」标题，但行文按概念链/主题分组组织（bullet 无 `- YYYY-MM-DD |` 前缀），既有模板与内容结构混用。实测 `Personal-AI-OS-概念-20260904.md`：当日建档（头部「来源：…灵感 + 与 GPT 深聊」+ mtime 今日），今日碎片行命中 0，却因含碎片积累标题落入「更新候选」而非「新建」。修正：含碎片积累标题的文件若今日碎片行命中为 0 且 mtime 为今日，不能默认归「更新」——read_file 头部确认「建档/来源」日期，建档为今日则归「今日新建知识文档」（不计碎片条数）；「新建 vs 更新」的最终裁决依据是文档头部日期标注 + mtime，不是区块结构。

**变体——文件名日期后缀 ≠ 创建日期（2026-09-10 实测）**：`projectx-direct-audio-baseline-执行档-20260908.md` 文件名带 9/8 后缀，但 os.stat 的 st_ctime=mtime 均为今日 21:07——实为当日重建/重写的既有文档。st_ctime 在此环境可近似创建时间（新建文件 ctime=mtime=当日）：文件名带旧日期后缀 + ctime 为今日 → 当日重写，read_file 内容确认升级记录后按「更新」汇报（本例为执行档补 Contract v1.0 + t08 v0.2 升级段），不占「今日新建」名额、主题数 N 不因此变化。裁决信号优先级：文件名后缀 < 头部日期标注 < st_ctime/mtime。

**变体——st_ctime 也会说谎：整体重写刷新 ctime（2026-09-14 实测）**：`家庭-孩子研究生.md` ctime=mtime 均为今日 14:49，按上例应判「今日新建」——但文件内容含早至 8/23 的日期条目，session_search 翻到 8/24 会话摘要明确记载当日建档。实为既有文档当日被 write_file 整体重写（追加条目走了全文覆盖而非 append），inode 更新连带重置 ctime。ctime=今日只是「新建」的必要条件非充分条件：内容含早于今日的日期条目、或会话史有更早建档记录时，判「更新」不占新建名额。ctime/mtime 与内容冲突时，信内容+会话史。

**变体——反向：建档晚于内容日期（2026-09-29 实测）**：`agnes-ai-定价.md` ctime=mtime 均为今日，但内容标注「2026-09-06 抓取」——内容是旧的、文件是今日新建（早前抓取的材料今日才落盘建档）。与 9/14 情形互为镜像：ctime=今日 + 内容日期全旧 ≠ 一定是重写。裁决技巧：用总数算术交叉验证——昨日总结报的主题数 N（如 115）+ 今日 ctime 为今日的文件数（6）= 今日扫描总数（121），对得上则 ctime-今日文件全部是真新建；对不上再逐个查会话史。汇报时给这类文档注明「内容 X 日期抓取、今日建档」，按新建计、不按更新计。

**原文归档目录——data/documents/（2026-09-02 确立）**：用户规则「外部文档/测试报告除提炼核心结论外，原文必须完整归档，不得只存结论」，归档位置为 `data/documents/`（与 data/ 下其他子目录平级，但未列入 AGENTS.md 目录清单，属新增约定，已同步进 fragment-catcher）。对知识汇报的影响：①方法 C/E 命中新建独立文档时，其头部常标注 `> 原文归档：data/documents/xxx.md`——汇报时确认原文确已落盘，可一行带过（如「原文归档 data/documents/xxx——新规则首次落地」），作为归档闭环的证据；②`data/documents/` 下的原文文件**不计入**知识主题数 N（N 只统计 knowledge/ 非模板文件），方法 B 扫到该目录有新文件属正常（会话中上传的外部文档落盘），不是知识碎片；③knowledge/ 主题文件 + data/documents/ 原文的双文件结构是预期形态，不是重复存储，不需要合并或去重。

**知识更新的来源归因——cron 推送产物（2026-09-20 实测）**：知识文件的当日新增可能来自定时研究 cron（如「家人就业政策跟踪-5省市」）而非用户口述。核对方法：扫该 cron 的今日 output Response 段——若推送成功（jobs.json last_delivery_error=None），说明详情用户已收到，知识区汇报只标来源与主题、一行带过（如「9/20 政策跟踪——早上跟踪 Cron 已推送过详情」），不重罗列推送内容；若该 cron 推送失败，才需在总结中补关键增量。

**第四种盲区——执行日期过后的闭环检查（2026-08-27 实测）**：带未来执行日期的计划文档在执行日当天往往仍是「执行前状态」（mtime 停在创建日）。当日记/事件出现对应里程碑完成记录（如「全新安装 Debian 13 完成」）而计划文档未更新时，在善意提醒中提议补记结果。实测：`projectx-n305-reinstall-btrfs.md`（8/26 创建，标注 8/27 执行）在装机完成日 mtime 仍为 8/26，晚间总结提议「补一笔实际结果（清华源、snapper #1）」。识别方法：知识汇报阶段若文档零新增且 diary/events 有对应执行里程碑 → 检查该文档 mtime 是否早于执行日。

**方法 D（文件删除检测——新增 2026-07-17）**：知识文件可能被用户删除或移入 archive。今日 session 中用户删除了两份与产品定义冲突的 GPT 生成文件（SSOT v4.0、v1.2 违规示例）。检测方法：

1. 用 `session_search(query="YYYY-MM-DD 删除 知识 knowledge")` 或类似查询获得当日会话摘要
2. 从摘要中提取文件删除事件的具体路径和原因
3. 交叉验证：列出 knowledge/ 下所有文件，看 session 中提到的文件是否确实不存在
4. 在知识积累汇报中添加「已删除」条目，与新增文档并列展示

示例检测代码：
```python
# 从 session_search 结果中提取删除事件
# session_search 返回的文本中可能包含 "已删除"、"删除"、"清理" 等关键词
# 搜索 "delet" "删除" "清理" "移除" "删掉" 模式
deleted_patterns = r"(删除|delet|清理|移除|删掉|移入.*archiv)"
# 匹配到后，提取被删除的文件名和原因
# 在知识积累汇报中以独立行展示
```

输出示例（整合到知识区块）：

```
  └── 今日新建知识文档：
      ├── 长期项目X 架构说明 v3.0
      ├── 长期项目X 开发方法 v3.5

  └── 已删除：
      └── SSOT v4.0、v1.2 违规示例（与产品定义冲突）
```

**方法 E（章节追加检测——新增 2026-08-09）**：知识以「给已有文档追加编号章节」的形式新增（实测：`projectx-competitora-local-llm-analysis.md` 新增「## 七、LFM2.5-2.6B 调研（2026-08-09）」「## 八、MiniCPM5-2B 补充（2026-08-09）」）。这类新增既不是碎片行（方法 A 漏检），也不在文件开头 500 字符内（方法 C 漏检），会导致「今日 0 新增」误报。检测方法：

1. 对 knowledge/ 下所有非模板文件，在**全文**（而非前 500 字符）搜索今日日期：`re.search(rf"{re.escape(today)}", content)`，或匹配标题括号日期模式 `## .*（YYYY-MM-DD）`
2. 命中但非碎片行 → 章节追加型新增，计入对应主题的「今日更新」，不按碎片条数计
3. 汇报时归入知识区块的更新列表，注明「XX 文档新增章节：…」
4. **交叉验证 session 摘要**：session_search 摘要声称「已截断/未归档」时，先读文件确认——摘要可能滞后于实际写入（2026-08-09 实测：摘要称 MiniCPM5-2B 结论未归档，实际 section 八 已完整写入；若直接采信摘要，会给出错误的「建议补录」提醒）。摘要中的**数字统计同样滞后**——如「累计 N 条」是写入时刻的中间快照（2026-08-19 实测：摘要称 CodeX.md「累计 12 条」，文件扫描实为 13 条，以文件扫描为准）。

**方法 A & B 的注意事项**——过滤掉 `_` 前缀的模板/示例文件：
```python
import glob, os
for f in glob.glob(os.path.expanduser("~/.hermes/data/knowledge/*.md")):
    if os.path.basename(f).startswith("_"):
        continue  # 跳过模板文件
```

**重要——正则必须兼容无 HH:MM 的格式**：知识碎片文件中的条目格式并非始终严格遵循 `- YYYY-MM-DD HH:MM |` 规范。实测发现 项目Y-长期项目X.md、prompt-engineering.md 等文件使用了省略 HH:MM 的格式（`- YYYY-MM-DD | 内容`）。如果检测正则强制要求 HH:MM，新增碎片会被完全漏掉，导致知识积累汇报显示「0 new」但实际有大量新增。**务必使用 `(?: \d{2}:\d{2})?` 使时间戳可选**。all_fragments（累计总数）的检测正则同样需要此调整，否则累计计数也会偏少。

**重要——同一正则也会误计「待消化/连接点」条目（2026-08-18 实测）**：`^- YYYY-MM-DD(?: \d{2}:\d{2})? \|` 同样命中 `## 待消化`、`## 连接点` 区块的行（格式同为 `- YYYY-MM-DD |`，无 HH:MM），导致「今日新增」虚高。实测花叔-AI技术资料.md 实为 3 条碎片 + 1 条待消化，未排除时计为 4。修正：按 `## ` 标题切分 content（`re.split(r"^## ", content, flags=re.M)`），只在「碎片积累」区块内计数；或单独扣除待消化/连接点区块内的命中数。汇报时待消化条目不按碎片计数。

**锻炼完成情况**
使用两阶段检测法，避免关键词的虚假匹配（如"没做锻炼""停练一天"等否定匹配）。

第一阶段——正向信号搜索：在当日 diary 和 events 中搜索明确的完成信号
- 正向模式：`(锻炼[完做]成|完成.*?(?:锻炼|运动)|全套锻炼|体育锻炼|锻炼(?:了|过|完|下))`
- 补充关键词：跑步、散步、深蹲、俯卧撑、拉伸（但仍需配合正向模式过滤）

第二阶段——排除否定匹配：如果匹配行中包含否定词（没做、没、停练、休息、未），标记为未完成

若两阶段后仍无正向匹配 → 今日未完成锻炼。

`execute_code` 实现范例（替换 today 为实际日期）：
```python
positive = r"(锻炼[完做]成|完成.*?(?:锻炼|运动)|全套锻炼|体育锻炼|锻炼(?:了|过|完|下))"
negative = r"(没做|没|停练|休息|未)"
matched = False
for line in diary_lines + events_lines:
    if re.search(positive, line) and not re.search(negative, line):
        matched = True
        break
```

**锻炼检测陷阱（2026-07-23 实测）**：原正则 `完成.*[锻炼运动]` 的字符集 `[锻炼运动]` 会匹配「提炼」「运行」等无关字眼（字符类匹配单一字符，非完整词），导致错误标记为「锻炼已完成」。必须使用非捕获组 `(?:锻炼|运动)` 匹配完整词语。

**锻炼检测陷阱（2026-08-28 实测）**：正向模式曾只覆盖复合结构（锻炼完成/完成锻炼/全套锻炼/体育锻炼），漏掉独立的「锻炼了/锻炼过/锻炼完」动词用法——日记写「锻炼了半小时」会被误判为未完成。在正向模式中补入 `锻炼(?:了|过|完|下)` 分支。

**获取今日会话上下文**

注意：`session_search` 是**独立工具**（direct tool），不是 `hermes_tools` 的导入函数。
不能在 `execute_code` 中 `from hermes_tools import session_search`——会报 ImportError。
应当在外层直接调用 `session_search()` 工具，或在 `execute_code` 之后单独调用。

**Pitfall——纯日期查询可能零结果（2026-08-18 实测）**：`session_search(query="2026-08-18 OR 8月18日")` 返回 0 条，但当天实际有 3 个会话（无参浏览 recent sessions 清晰可见）。日期字符串分词不稳定，纯日期查询容易漏。正确姿势：①先无参调用浏览最近会话，确认当天有哪些会话；②用日记/事件中的内容关键词查询（如「编程机 OR 产教融合 OR 花叔」命中正常）。不要把「查询零结果」当作「当天无会话」的证据。

正确用法：
```
# 外层直接调用
session_search(query="YYYY-MM-DD")
```

获取当天各次会话的摘要（早间简报内容、碎片捕获记录等），帮助了解用户全天节奏和未完成事项。

**摘要不可用时的工件重建（2026-09-14 实测）**：session_search 可能返回 `[Raw preview — summarization unavailable]`——大会话（实测 82 条）摘要生成失败，只剩首条消息预览，整天内容拿不到。此时改从落盘工件交叉还原：① todos.json 的 mtime + 待办文本中的当日变化（实测 dl-039 文本 16:17 更新出「维护单位已拉走」）；② knowledge/ 文件 mtime 与内容中的今日条目；③ 当日已触发的提醒 cron output（给出触发时点状态快照，如「09:01 提醒时 done 仍为 false」）；④ 各工件时间戳拼出会话活动区间。工件覆盖「做了什么、何时做」，原话措辞拿不到——汇报按工件事实写，不虚构会话细节。

**会话时间轴锚点（2026-09-25 实测补充）**：摘要不可用时，无参 browse 返回的会话元数据可直接定全天节奏——started_at/last_active 给出工作时段（如 12:12-18:00），message_count 区分主会话与碎片会话（224 条 vs 2 条）；preview 字段常保留用户开场原话（如「n305已布置完毕，我们可以开始测试的准备」），拿它作叙事锚点即可，不必硬凑日记措辞。与 knowledge/documents 的 mtime 链拼起来，足以还原一天主线。

**提示**：如果今日有早间简报（08:30 Cron 推送），它的输出已涵盖连续静默天数、待办概况等信息。晚间总结应避免重复已说过的内容——引用简报结论而不是重新罗列一遍。用 `session_search` 获取简报摘要，只需补充简报之后发生的变化。

**补充场景——简报 cron 失败但已在会话中手动补推（2026-08-21 实测）**：当日早间简报 cron 报错（如 SSL 瞬断、网络侧故障），但上午会话中已排查并手动把简报内容发给了用户 → 晚间总结只需一句带过（「早上的简报因网络瞬断没自动推，已在会话里补了」）。**不要重复罗列简报里的待办清单**——用户已经看过，再列一遍是噪音。故障细节（错误码、重试次数、排查过程）不重复描述，除非有新的进展。

**思考会话检测（新增 2026-07-29）**

用户有时会发起深度思考会话（架构设计、战略规划、理论学习、认知突破等），这些会话产生了当天最重要的认知产出，但内容未写入知识文件。这是**非异常的正常模式**——用户选择将思考留在对话中而非持久化到 knowledge/。

检测方法：在 session_search 获取的会话摘要中识别以下信号：
- 长时间、多轮次的深度讨论（非单条碎片输入）
- 涉及认知突破性表述："定稿""定型""冻结""里程碑""认知突破""核心公式"
- 有完整的推导链条或理论建构（从 A→B→C 的推理过程）
- 用户语气专注、好奇、投入（非琐碎事务型）

与非思考会话的区分：日常事务型会话（"到货了""已发送""正常上班"）不应标记，只在有明显的认知产出或深度建构时触发。

**检测后处理**：在输出结构的 📖 今日日记后添加一个「💬 今日思考」区块（见输出结构说明），将思考内容浓缩为自然叙述呈现。同时检查思考中产生的认知结论是否值得提议写入 knowledge/——如果是重要的架构定稿或认知突破，在善意提醒中加一句温和提议。

**月份文件今日新增**（expenses/YYYY-MM.md）
```
search_files(pattern="YYYY-MM-DD ", path="~/.hermes/data/expenses/YYYY-MM.md")
```
无匹配则今日无记账。

**Pitfall——文件不存在的情况**：如果该月份尚无任何记账记录，expenses/YYYY-MM.md 文件根本不存在。此时 `search_files` 返回的是路径不存在错误（而非零匹配结果）。需要先 `os.path.exists(目标路径)` 确认文件存在，再用 `search_files` 搜内容。execute_code 中直接 open + search 会触发此问题——改用 `os.path.exists` 前置检查，文件不存在则直接判定「本月无记账」。

**todos.json 顶层扫描陷阱（2026-09-27 实测）**：todos.json 顶层除 `quick_tasks`/`deadlines`/`projects` 三个数组外，还有 `_` 前缀的元数据键（`_说明` 为字符串、`_格式说明`/`_ID规则` 为 dict）。用「遍历全部顶层 key → 对元素调 .get()」的扫描脚本会先撞上元数据键直接 AttributeError（`'str' object has no attribute 'get'`）。修正：只遍历三个已知数组键（或跳过 `_` 前缀键），并对值先判 `isinstance(list)` 再下钻。

**批量数据采集**（使用 execute_code 替代逐文件 read_file）：
当需要同时检查多个 knowledge 主题文件（今日新增碎片）、或多个日记/事件文件时，
用 `execute_code` 配合 `from hermes_tools import read_file, search_files` 一次搞定，
比逐个 `read_file` 更高效。

示例（替换 YYYY-MM-DD 为实际日期）：
```python
# 注意：知识碎片行的格式通常是 "- YYYY-MM-DD HH:MM | ..."，
# 但部分文件省略了 HH:MM 时间戳（如 "- YYYY-MM-DD | ..."），
# 所以正则中 HH:MM 部分设为可选。
from hermes_tools import read_file, search_files
import glob, re, os
today = "YYYY-MM-DD"
base = os.path.expanduser("~/.hermes")

# Part 1: 碎片格式检测（方法 A）
fragment_topics = {}
for f in glob.glob(os.path.expanduser("~/.hermes/data/knowledge/*.md")):
    basename = os.path.basename(f)
    if basename.startswith("_"):
        continue
    content = open(f).read()
    # 今日新增碎片数（HH:MM 可选，兼容两种格式）
    new_matches = re.findall(rf"^- {re.escape(today)}(?: \d{{2}}:\d{{2}})? \|", content, re.MULTILINE)
    # 累计碎片总数（同样兼容两种格式）——⚠️ 必须与上一行同为 rf-string：
    # r"" 配 {{2}} 的混用，在普通正则里会要求文本出现字面 {{2}}，所有带 HH:MM 的行被静默漏计
    # （2026-09-18 实测：新文件 5 条全时间戳碎片，today=5 而 total=0——「新增正常、累计归零」即此签名）
    all_fragments = re.findall(rf"^- \d{{4}}-\d{{2}}-\d{{2}}(?: \d{{2}}:\d{{2}})? \|", content, re.MULTILINE)
    all_topics[basename] = {"new": len(new_matches), "total": len(all_fragments)}
    if new_matches:
        fragment_topics[basename] = (len(new_matches), len(all_fragments))
        print(f"{basename}: {len(new_matches)} new, {len(all_fragments)} total")

# 总主题数（用于"知识库维持 N 个主题"行）
print(f"\n总主题数（非模板）: {len(all_topics)}")

# Part 2: 独立文档检测（方法 C）
standalone = []
for f in glob.glob(f"{base}/data/knowledge/*.md"):
    fname = os.path.basename(f)
    if fname.startswith("_"):
        continue
    if fname in fragment_topics:
        continue  # 已在碎片列表中，避免重复
    content = open(f).read()
    if "## 碎片积累" not in content and re.search(rf"{re.escape(today)}", content[:500]):
        standalone.append(fname)
        print(f"[DOC] {fname}: standalone document created today")

if standalone:
    print(f"Standalone documents: {standalone}")
```

**日记 vs 事件文件格式差异**：diary/ 使用 `-` 项目符号格式（`- HH:MM | 内容`），events/ 使用 `|` 表格格式（`| HH:MM | 事件 |`）。批量采集时不要用同一套解析模式处理两种文件——用 `read_file` 按各自格式分别解析。diary 的 `execute_code` 正则应匹配 `^- \d{2}:\d{2} \|` 而非 `|` 表格分隔符。

**⚠️ events 格式不稳定（2026-08-10 实测）**：events/ 文件实际也可能用 `-` 项目符号格式（`- 07:42 | 内容`）而非文档所述的 `|` 表格格式。若只按 `|` 开头过滤会**全部漏掉**——实测误报「events 0 条」，实际文件有 4 条事件，直到 read_file 直读才发现。解析时应同时接受两种格式，例如：
```python
if l.strip().startswith("|") or re.match(r"^- \d{2}:\d{2} \|", l.strip()):
    events_lines.append(l.strip())
```
批量结果为零时，务必用 read_file 直接读文件确认是真空还是解析遗漏（events 内容常与 diary 重叠，可交叉验证）。

**日记时间戳晚于触发时间（2026-09-09 实测）**：22:00 Cron 触发时，当日 diary/events 可能已含晚于 22:00 的时间戳条目（实测含 23:30/23:45 条目）——碎片落盘时间戳由写入方生成，与 Cron 触发时钟不同步，另 events 可能比 diary 少收最后几条（以 diary 为全量源）。处理：照抄原始记录的时间戳呈现（「日期只引用原始记录」同样适用于时间戳），不质疑、不换算、不因「还没到点」而跳过条目。

**Python f-string 陷阱**：在 `execute_code` 的 f-string 表达式中不能使用反斜杠转义（Python 3.11 及更早版本的限制）。
```python
# ❌ 会报 SyntaxError
print(f"行数: {len([l for l in lines.split('\\n')])}")

# ✅ 正确做法：将反斜杠表达式提取到临时变量
newline = "\n"
print(f"行数: {len([l for l in lines.split(newline)])}")

# ✅ 或用 % 格式化绕开
print("行数: %d" % len(lines.split('\n')))
```

**安全提示**：Cron 环境的 `terminal` 对 `python3 -c` 内联脚本和 pipe-to-interpreter 模式
（如 `cat file | python3 -c`）有安全拦截，无法使用。需要解析 JSON 或做复杂数据处理时，
务必使用 `execute_code` 工具而不是在 shell 中调用 Python。

**execute_code 全新解释器陷阱（2026-08-20 实测）**：每次 `execute_code` 调用都是全新的 Python 进程，`import json`、`import glob` 等必须**在每个脚本内重新声明**——上一个脚本里 import 过的模块下一个脚本不会保留。实测同一天内连续两次 NameError（json、glob），均因沿用上一个脚本的 import 假设。多步采集拆成多个 execute_code 时，每个脚本头部完整写 import，不要省。

**已验证的备选模式**：当 `execute_code` 的 `from hermes_tools` 导入失败或返回值格式异常（如 `KeyError: 'content'`）时，使用以下模式绕开：
1. 用 `write_file` 将脚本写入 `/tmp/script.py`（纯 Python，不使用 hermes_tools，直接 open + 标准库解析文件）
2. 用 `terminal('python3 /tmp/script.py')` 执行并获取输出
示例：数据分析脚本写入 `/tmp/analyze_todos.py`，内容为 `json.load(open("~/.hermes/data/todos.json"))` 标准库操作，可稳定运行。

**早间简报原文定位**：daily-briefing 的 cron 输出文件（`cron/output/<job_id>/<date>.md`）中，Prompt 段包含完整 skill 全文，实际推送内容在 `## Response` 标记之后。直接读输出文件可拿到简报原文，与 session_search 摘要互为补充（摘要偏事件概括、原文偏措辞细节），用于「引用简报结论而非重新罗列」时准确还原简报说了什么。

**Pitfall——定位 Response 必须用 rfind（2026-08-18 实测）**：Prompt 段嵌入的 skill 全文自身含多个字面 `## Response` 字样，`content.find("## Response")` 会命中 skill 正文而非真实推送内容（首次读取时抓到的是一大段技能文档）。正确做法：`idx = content.rfind("## Response")` 取最后一次出现再截取。同理适用于任何带完整 skill 全文的 cron output 文件。

**rfind 盲区——失败运行根本没有真实 Response 段（2026-09-14 实测）**：cron 中途超时失败时（连续两晚实测 `TimeoutError: idle for 601s/604s — last activity: executing tool: session_search`），输出文件只有 Prompt 段（含 skill 全文）+ 末尾 `## Error` 段，此时 rfind("## Response") 仍会命中 skill 正文里的字样（实测命中处仍是技能文档），误判「有 Response」。可靠判法：正则枚举全部 `^## ` 标题看文件结构——末尾标题是 `## Error` 即失败运行；真实 Response 必须位于最后一个 skill 文本标记之后。同型超时连续出现时按「连续第 N 晚」口径汇报，不重新诊断。

**Response 段内嵌同名标题——按下一个 ## 截断会静默丢内容（2026-09-15 实测）**：真实 Response 的正文经常自带完整输出结构标题（如 `## 📋 今日回顾 · YYYY-MM-DD`）。用「截取到下一个 `^## ` 标题」的逻辑取 Response 段时，只会拿到开头引导语——实测只取到「写入验证通过。今晚总结如下。」一行，文本通顺、内容被静默截断，差点据此误判昨晚总结没写过什么。正确做法：rfind 定位后取固定宽度窗口（idx 到 idx+4000 左右）或直接读到文件尾，不在 Response 内部按标题再切。防重复提醒核对、引用简报结论都依赖 Response 全文，截断会把「提过」误判成「没提过」。

**search_files 静默零命中陷阱（2026-09-07 实测）**：对 `~/.hermes` 下文件用 `search_files` 搜索中文内容可能静默返回 0——实测对 `memory/mood-trends.md` 两次搜索（`### 2026-09-06 情绪评估`、锚点标题正则）均 `total_count: 0`，但 read_file / execute_code `open()` 明确读得到内容。`~/.hermes` 是 data-backup 的 git 仓库，ripgrep 默认尊重 .gitignore，被忽略或处于规则边界的文件会被静默跳过。教训：**search_files 零命中 ≠ 内容不存在**——凡是要以「搜不到」下结论的检查（某文件有无今日条目、锚点是否存在、某行有无出现），改用 read_file 直读或 execute_code `open()` 复核后再定论。全文搜索若返回异常少的结果，优先怀疑搜索器而非数据。

**系统健康信号——memory 写入失败**：session_search 摘要中若出现 memory 写入失败信号（「记忆容量满」「2187/2200」「threat pattern 拦截」「写入失败」等），说明工作记忆层接近饱和或触发安全拦截（2026-07-31 实测：一次因提及 .env 被 threat pattern 拦截，一次因容量满）。**直接验证方式（比摘要更可靠，2026-08-20 实测；路径修正 2026-09-29）**：注入层本体是 `~/.hermes/memories/MEMORY.md`（§ 分隔条目），用 execute_code `len(open(...).read())` 数字符，不受编码干扰。`~/.hermes/MEMORY.md`（无 memories 子目录）是旧架构遗留索引，2026-07-09 起停更，勿混淆（9/29 曾因路径混乱险些清错文件）。接近上限即为饱和信号；**水位 ≥1900 时按步骤 7.5 自主 consolidation，不再只提醒用户**（2026-09-29 升级：清理动作从「提请用户」改为 cron 自主执行，快照回滚锚点先行）。⚠️ **`wc -c` 返回字节数，上限 2200 是字符数**——中文 UTF-8 每字约 3 字节，字节阈值 ≈ 6600（2026-09-08 实测：读到 4894 字节，若误当字符数会虚报「超限一倍」；实际 ≈1630 字符，健康水位）。最稳妥的做法是用 execute_code `len(open(...).read())` 数字符，不受编码干扰。接近上限即为饱和信号；超限属重度饱和（2026-09-09 实测 3180/2200，文件仍可读），提醒时直接报实测数值（如「已到 3180/2200，下次写入可能失败」），属观察类信号、不当故障处理；明显低于上限（如 1600 字符出头）说明已清理过，不必提醒。摘要可能滞后于实际清理——以文件实测为准。**接近饱和但写入成功的信号同样值得提醒**：摘要出现「精简后写入，2,190/2,200 chars」这类描述时（2026-08-09 实测），说明已到 99% 容量，下一次写入随时可能失败——与写失败同等对待，在善意提醒中自然提一句「记忆层快满了，改天有空清理合并一下旧条目」。这值得在善意提醒区块中以自然语气提示用户（如「记忆容量快满了，今天有两次记忆写入失败，改天有空清理合并一下旧条目」）——用户不被告知就不会知道后续新记忆可能存不进去。这是观察类信号，不是待办，不需要修复动作。

**系统健康信号——备份 Cron 被注入扫描器拦截（新增 2026-08-08）**：检查 data-backup job 的 output 目录（`~/.hermes/cron/output/<job-id>/`，job id 从 jobs.json 按 name=data-backup 查）今日输出文件，若显示 `Status: BLOCKED` 且提示 `prompt matches threat pattern ...`（如 `exfil_curl_auth_header`），说明该 job 关联 skill 的内容命中了 cron 威胁正则，备份未运行（jobs.json 中 last_status=error）。这是可修复的系统问题——改写 skill 中触发模式（如 curl 的 Authorization header 改为变量间接引用）后即可恢复，详见 data-backup skill 已知陷阱表。晚间总结应在善意提醒区块告知用户拦截事实与修复状态，并顺带检查 git log / backup-status.json 判断积压程度（本地 commit 通常已保全，远程同步可能中断）。检测时机：扫描 cron output 目录时一并查看，不单独增加步骤。

**泛化——非备份 job 同样可能被拦（2026-09-01 实测）**：`v04-24h收尾`（测试硬件N 24h 稳定性测试的 SSH 详查收尾轮）被 `ssh_backdoor` 威胁模式拦截——job 合法需要 SSH 命令，属误伤。关键区分：同批的每小时监控 job 不受影响、照常 PASS（180 周期零异常），只是收尾轮没跑。处理与备份被拦相同——善意提醒中告知拦截事实 + 修复路径（改写 job 的 prompt/skill 内容规避威胁模式后重跑），不夸大为数据丢失。检测时对**所有**今日 job 输出都留意 `Status: BLOCKED`，不限于 data-backup；引用技能全文的 output 文件同样用 rfind 截取 Response 段再判断。
正常对照：备份健康时今日输出文件的 Response 段为 `[SILENT]`（无变更可推送，属预期状态）——不要误读为失败；只有 `Status: BLOCKED` 或 jobs.json 中 last_status=error 才需要提醒用户（2026-08-19 实测：备份输出 [SILENT] 且 last_status=ok，正常）。同类的正常静默还有：`no_agent` 轮询类 job（如 workbuddy 成长中心轮询）Response 段为空属预期——无事不报的看门狗模式，last_status=ok 即健康，不要当失败处理（2026-09-20 实测：轮询 job 21:10 首轮运行，Response 空、状态 ok）。

**检测陷阱——状态关键字全文搜索误报（2026-08-30 实测）**：检测 BLOCKED/error/failed 等状态时，**不要全文搜索**（`"BLOCKED" in content`）——cron output 文件的 Prompt 段嵌入了完整 skill 全文，其中自带 `Status: BLOCKED`、`## Error` 等示例文本，全文搜索必然命中、误报为「备份被拦截」。正确姿势：先 `idx = content.rfind("## Response")` 截取 Response 段（rfind 取最后一次出现，理由见 8/18 实测），再在该段内检查关键字；或直接通读 Response 段内容判断（本次实测：Response 段为「备份完成，全程无异常…[SILENT]」即健康，全文却含 BLOCKED 字样）。同理适用于一切带完整 skill 全文的 cron output 文件的状态检测。

### 步骤 7.5：记忆 consolidation（水位触发，2026-09-29 新增，借鉴 Letta dreaming）

检查注入层水位：`len(open('~/.hermes/memories/MEMORY.md').read())`（字符数，上限约 2200）。
⚠️ 路径是 `memories/MEMORY.md`（Hermes memory 工具的活跃存储），不是 `~/.hermes/MEMORY.md`（旧架构遗留索引，7/9 起停更，勿混淆）。

- **每晚先记录水位趋势（无条件执行，2026-09-30 新增，借鉴 某AI通道服务 记忆占用百分比）**：append 一行 `YYYY-MM-DD|字符数|条目数` 到 `~/.hermes/data/journey/waterlevel.log`（月度回放的天然数据源），并与昨日值对比；在总结补充区块报一行「🧭 记忆水位 N/2200（P%），较昨日 ±M」。趋势是决策信号：快涨=记太杂该挤水，平稳=健康。**首晚（log 无前日记录）只报当前值，不报趋势**
- **水位 < 1900（86%）** → 趋势记录后跳过，不做整理
- **水位 ≥ 1900** → 执行一轮整理，输出一行说明（如「🧹 记忆整理：28→26 条，2180→1966」）：
  1. 整理前快照：`cp ~/.hermes/memories/MEMORY.md ~/.hermes/memories/MEMORY.md.pre-consolidation`（回滚锚点，覆盖旧快照即可）
  2. 合并同主题条目（运维类、工具链类多条合一）
  3. 删除已过期事实（已完结的截止、被翻案的中间结论、已变化的瞬时状态）
  - **整理判据（2026-09-30 新增，借鉴 某AI通道服务 原理篇写入标准）**：①三个月判据——该条目三个月后是否仍然成立？不成立的删除或降级到 knowledge/ 留痕；②状态类条目必须带时间锚（如「血压 7/12 起」），无锚的过期事实冒充「当前状态」风险最高
  4. 压缩表述（去冗余括注；与 USER.md 重复的画像细节改指针）
  5. **硬约束——事实无损**：决策类条目（拍板/冻结/规则/教训）只压措辞不删内容；拿不准是否过期的保留
  6. 写入后复测水位，在总结的补充区块报一行结果。**评估后无可整（判据全过、无合并组、措辞已密）也是合法产出**——同样报一行评估结论（如「🧹 记忆体检：29 条全过判据，无可整，水位 2099」），不做名义性压缩；该状态说明水位上涨来自高价值新增而非垃圾堆积

**首次实战打法（2026-09-29 实测，2197→1894 三轮完成）**：
- **整档重写优于逐条 patch**：条目多时（27+ 条），在 execute_code 里重建 entries 列表整体写回，比逐条 patch 快且不会误伤；快照先行即是回滚锚点，整写可接受。
- **三轮压缩的收益结构**：第 1 轮逐条措辞压缩（去冗余括注/历史细节如「9/6修pgrep自匹配」）只省 ~130 字符；第 2 轮砍前缀与重复修饰（「编码分工→分工」「重要任务→任务」）再省 ~90；真正达标靠第 3 轮的两个判断——①先查 USER.md 是否已有同内容（本例 USER.md 无锻炼/孩子/血压等，只能压不能删）；②INDEX.md L1 分层上线后，已完结事件的 knowledge 指针可退役给索引层（实测退役电视盒子A指针 1 条，内容在 knowledge/ 完好）。
- **事实无损的验证方法**：重写前列一份 must_have 关键词清单（每个事实一个标记，~30 个），写回后逐个 `in check` 验证，缺失项逐个确认是「有意退役」还是「误删」。报告报实测数（如「2197→1894，27 条」）+ 快照位置。
- **收益预期管理**：§ 条目式注入层，纯措辞压缩每轮上限约 10-15%；水位超限严重时（如 >2400）指望措辞压缩不现实，必须靠合并条目 + 删过期事实。

**第二轮实战（2026-09-30 实测，2197→2086 单轮完成）**：
- **收益结构反转**：首轮已把措辞压过一遍后，第二轮纯措辞压缩空间枯竭（本轮仅省 ~40）；主要收益来自**合并内容重叠的条目**——PAOS 概念条与 MyPS 定位条都讲「MYPS=延伸、LUMA=它」，合并为一条 PAOS 条目（保留思想助手/三层身体/全自动批判五刻度/竞品三目的，指针同指 knowledge 两文档）省 ~180。合并优先找「同一主题被多条从不同日期写入」的簇，不是找废话。
- **must_have 清单法二次验证通过**（61 关键词全过），整档重写照常安全。
- **waterlevel.log 同日多行合法**：白天会话写入方与晚间 daily-review 各记一行（实测 `2026-09-30|2099|29` + `2026-09-30|2086|28`），两行都是事实，月度回放按行序看演化即可，不要去重。
- 压缩后仍在 ≥1900 也是合法终态——报实测值即可，不为凑线硬删拿不准的条目（如带时间锚的健康计划）。

**第三轮实战（2026-10-01 实测，2173→2124 单轮完成）**：
- **少量编辑用 execute_code 精确串替换，不必整档重写**：3-5 处压缩/合并时，每处 old 串先 `count == 1` 断言（不唯一即 abort），全部通过后才写回一次——比逐条 patch 快、比整档重写风险面小（实测 abort 时文件未动，只有快照与 pre 行已落盘）。
- **合并编辑先验相邻性**：§ 条目散布全档，凭 dump 顺序印象假定两条相邻会翻车（实测 Hermes CLI 是第 1 条、记忆存储是第 26 条，直接合并编辑 count=0 abort）。正确拆法：两个编辑——①删除独立条目行（连同其后 `§` 分隔行），②把内容折进目标条目开头（改前缀）。
- **abort 后重跑必须幂等**：脚本中途 abort 时 waterlevel pre-line 与快照已写入——重跑前先比对 log 末行是否等于本次 pre 值，等值则跳过追加。同日多行合法的前提是「每行都是事实」，abort 重跑产生的重复行不是事实，要防。
- 收益参考：4 处编辑（3 压缩 + 1 合并）省 49 字符；must_have 清单扩到 128 项仍全过，清单法随条目增长照常可用。

**events 与 diary 部分重合时（2026-09-16 实测）**：events 多数条目独立、少数与 diary 同事同刻双写（实测 6 条 events 中 2 条与日记重合、4 条独立）——不适用上面的完全重复规则。处理：日记区块照常全列，事件区块只列独立条目，重合条目合并为一行带过（如「└── 10:36、11:10 两条与日记重合，不重复列」），不逐条复述。判断重合的依据是事件内容与时间戳同时对上，不是标题相似。

**思考会话区块**：当「思考会话检测」（见数据采集部分）触发时，在 📖 今日日记和 💡 今日灵感之间插入：

```
💬 今日思考
  └── [思考内容的浓缩叙述——自然语言，不以碎片格式逐条列出]
```

与 💬 今日好句的关系：两者共用 💬 emoji，但上下文区分。思考会话放在日记后、灵感前；好句放在事件后、记账前。

### 2. 今日完成

列出今天标记完成的待办，以及每日必做事项的完成情况。**留意那些被更新/推进但尚未标记完成的待办**——例如用户修改了待办文本（合同已发出、状态更新等），虽然 done 字段仍为 false，但实际有进展。这些也值得在今日完成中提及，用区别于完整完成的表述（如「推进中」或「已更新」）。提交后被驳回的申报类待办同样算「推进了一轮」——尝试过、被拒、待整改重报，表述用「推进了一轮」，不标完成（2026-08-25 实测：dl-008 科技型申报提交后被拒，日记记录为推进状态）。

```text
✅ 今日完成
  ├── 给张总发方案（14:30 完成）
  ├── 🏋️ 今日锻炼已完成
  └── 买牛奶（18:00 完成）
```

如果今天没有完成任何待办 → 显示「今天没有完成事项。明天继续。」（语气平和，不带评判）

**高产出零销账日的变体（2026-09-28 实测）**：当天产出集中在日记/知识/仓库线（如镜像打通、脱敏上线、多篇知识文档落盘）但 todos.json 无任何销账时，不套用「今天没有完成事项」——那会错误暗示今天没干活。改写为一句「无待办销账——但产出全在文档和仓库里」，不罗列产出明细（日记/知识区块已呈现，重复即噪音）。

**到期日 ≠ 完成日（2026-09-10 实测）**：扫描 todos.json 时，deadline 恰为今日的批量件（如月度清单 dl-032~037，deadline 9/10）可能早已在之前完成（done_at=8/31、9/6）。判定「今日完成」以 done_at 为准，不以 deadline 归属——否则会把上周干完的活算成今日完成，虚报产出。deadline 在今日且已 done 只说明「本期清零、无逾期」，不进今日完成列表。

**deadline 字段可能已顺延（2026-09-10 实测）**：dl-008 的 deadline 字段已从原始到期日 8/31 顺延到 9/14——「逾期第 N 天」类计数（mood-trends 备注惯例）以原始到期日为准，不是 deadline 字段现值。输出中涉及逾期表述时先确认计期基准，拿不准就不写具体天数。

**Cron 环境下的待办状态同步**：当 diary/events 中明确记载某项待办已完成（如「出勤统计完成」「XX收尾」等表述），虽然 todos.json 的 done 字段仍为 false，应**主动更新** todos.json 的 done=true 和 done_at=today，而非等待用户确认。判断标准：
  - 必须明确提及该待办的具体内容或核心动词（如「出勤统计完成」→ 匹配「整理月度报表」）
  - 必须是完成陈述（「做完了」「完成了」「搞定了」「收尾了」），而非计划性陈述（「计划做」「准备做」「需要做」）
  - 如果只有一个模糊的完成信号（如「今天忙完了」但未指定事项），则不在系统内标注完成，仅在输出中提及「可能已完成，需确认」
  - 同时清理关联的 reminder_cron_id 对应的 Cron 任务
  因为这是 Cron 环境（无用户实时交互），不要留下「要不要我帮你标上」这类需要用户回复的问题——直接执行并说明即可：`已标注 dl-014 整理月度报表为完成。`

如果锻炼还没做 → 在今日完成末尾温和提示：
```text
  🏋️ 今日锻炼尚未完成。不限时间，睡前抽空做了就行。
```

**锻炼提示的防重复（2026-09-19 实测）**：断档计数照常在 mood-trends 备注中继承（数据层永不断档），但输出层的「🏋️ 尚未完成」模板提示同样受 2026-08-29 防重复规则约束——前一晚已提示且用户无响应时，本轮不重复催促模板。零录入日（无 ✅ 区块，标准提示位置不存在）最多在情绪区块收尾带一句不催促的轻描淡写（如「不催，哪天状态对了自然就捡起来」）。长期断档（几十天级别）每晚点名本身就是噪音：数据层记录 + 偶尔一句足够，连续两晚已提过就停。**简报同日已点名同理（2026-09-28 实测）**：早间简报「🏋️ 每日必做」区块已显示「今天还没做」时，晚间不再二次催促——同一天两次是噪音；mood-trends 备注的断档计数照常 +1，输出层静默即可。

**核对基准是推送的 Response 段，不是 cron 会话的 session 摘要（2026-09-21 实测）**：「信号在当晚 cron 会话内部被观察到」≠「写进了推送的 Response」——两者会脱节，候选提醒可能在观察与推送之间静默丢失。实测：MEMORY.md 超容信号（3180/2200）在 9/20 晚间 cron 会话摘要中有明确记录，但 9/19、9/20 两晚实际推送的 Response 段均未提及——用户从未被告知，本轮提及属首次告知而非重复。双向规则：①判断「是否已提过、用户是否已知情」只认 Response 段，session 摘要提过不算数；②扫描系统健康信号时若 session 摘要提及但近期 Response 段查无此句，视为待首次告知的候选，不因「摘要里说过」而跳过。

## ⚠️ 事实性防错规则（2026-09-09 简报事故后同步，生成式输出的硬约束）

1. **日期只引用原始记录**：待办/行程日期一律照抄 todos.json text 原始表述（如「9/11 上午 某车次」），禁止换算成「明天/后天/下周」等相对词——相对词换算已出过事故（deadline 9/11 被写成「明天去某市」）
2. **状态以最新档案为准**：在途/到货/已完成类状态必须查 data/events/ 与 data/diary/ 最近记录，禁止凭会话印象写（USB 麦克风 9/8 已到货接入仍被写「在途」的教训）
3. **推送前逐项自查**：所有日期与 todos.json/events 原始记录对照，不一致即返工
4. **简报日期事故的当晚纠正（2026-09-09 实测）**：当日简报已把相对日期写错（「明天去某市」实为 9/11）时，晚间总结除自身照抄原始日期外，须在善意提醒区块加一行明确更正（如「按 todos 原始记录是 9/11 上午 某车次 赴汉——后天出发」），并核对行前准备类 reminder cron 的排期是否与原始记录一致（本例「出发前准备 9/10 晚」排期正确，顺带一句「明晚提醒已排」让用户按正确节奏准备）。一行讲清正确日期即可，不展开简报故障细节、不检讨简报生成过程

5. **前晚总结自身的相对日期错误（2026-09-23 实测）**：相对日期写错的来源不止简报——前晚 daily-review 也会犯（实测 9/22 把 9/25 写成「后天 9/25」，实际从 9/22 算后天是 9/24）。处理同规则 4：当晚输出照抄 todos.json 原始绝对日期（如「中秋值班是 9/25（周五）日班，后天」），这本身即完成更正，不检讨前晚、不另开更正段。自查方式：凡输出里出现「明天/后天/下周三」等相对词，回查 todos.json 的绝对日期再换算一次——**相对词只在写出的那一刻算一次，绝不复用前晚输出里的相对词**。

## 输出风格规则

1. **搭档语气**：不是写报告，是和朋友聊今天的回顾
2. **简洁**：每个区块几行就够，不展开
3. **有选择性地呈现**：没有数据的区块直接跳过，不展示空区块
4. **温度适度**：不过度关心，也不冷冰冰
5. **不用感叹号**：用句号
6. **惊奇度和情绪融入自然对话**：不单独标注「惊奇度扫描结果」或「情绪分析报告」

## 月度总结扩展

当 cron 提示词或用户要求生成月度总结时，所有数据已在步骤 1 中采集完毕。无需额外数据收集。

具体分析框架和输出结构请参见 `references/monthly-summary.md`。月度总结不是独立 skill，它复用 daily-review 的数据管道和行为模式分析方法。

- **SKILL.md 不记录月总结细节**：请查阅 `references/monthly-summary.md`

## SILENT 决策指引

每天汇报还是静默？判断规则：

| 场景 | 决策 | 理由 |
|------|------|------|
| 用户当天有主动录入（日记/灵感/事件/待办完成/碎片等任何一项） | ✅ 正常输出 | 有内容需要回顾 |
| 用户当天零录入，但有关联上下文（今日有到期待办、有提醒已推送、有跨日计划） | ✅ 正常输出（简短版） | 虽然无新内容，但「没记录」本身是信息，且跨日计划需要关注 |
| 用户当天零录入，无任何关联上下文，系统也无任何事件 | ❌ [SILENT] | 真正没什么可说的 |
| 数据目录不存在或全部数据源无法读取 | ❌ [SILENT] | 基础设施问题，静默失败 |

**低数据日输出原则**：当用户零录入但有上下文时，输出控制在 5-8 行以内，跳过所有空区块，情绪评价一句带过。不要因为内容少就扩写凑数。

**零录入日输出格式**：当用户全天无任何录入（无日记/灵感/事件/碎片/待办完成）时，不使用标准的 emoji 区块格式（📖📰💡💬💰）。改用紧凑叙述格式，将所有内容合并为 3-4 个自然区块，使用 `###` 作为块标题：

```
## 📋 今日回顾 · YYYY-MM-DD（周日）

今天很安静，没有新的录入。[日期类型]，[节奏说明一句]。

**⚠️ 开场句写当日真实状态，不是默认模板**：若当日有活跃会话（见 emotion-coach「零录入 ≠ 零交互」规则），开场句直接叙述会话内容，**不要写「今天很安静」**——安静模板只适用于确认无任何会话的日子（2026-09-05 实测：休息日 + 10:42 模型切换实验会话，开场「今天休息。」后叙述实验进展与卡点，未用安静模板）。此类日子的会话叙述写进开场段（紧凑格式没有 💬 区块），情绪区块与补充区块照常。

### ⏰ 到期待办/需关注
[如果有关联上下文——到期待办、积压提醒等——在此行说明]
[如果没有上下文 → 跳过此区块]

### 📚 知识积累
    今日无新增碎片。知识库维持 N 个主题。

### 🌟 今日情绪
[情绪教练评价，一句带过]

### 💡 补充(可选)
[数据备份状态、前日遗留说明等系统级信息]
```

- 主标题用 `## 📋 今日回顾`（非 emoji 区块格式）
- 每个子标题用 `###` 而非 `📖`/`💡` 等 emoji 前缀
- 严格：只在有实际内容的区块上写标题，空区块全跳过
- 到期待办区块只在有当日截止或积压提醒时出现
- 情绪区块永远保留（最低限度一句）
- 情绪区块可以在一句基调后追加一句**上下文感知的收尾**（如明日行程提醒、健康叮嘱），而非严格一字不动的模板句——这符合「温度适度」风格，但只加一句，不扩写（2026-08-02 实测：「今天很安静。周日休息日，正常的休息节奏。明天出发去外地A，路上注意安全。」）
- 补充区块仅在有系统级信息时才出现（备份、前日异常等）
- 保持紧凑：每个区块控制在 3-4 行实际内容以内

**连续静默日处理**：当出现 2 天及以上的连续零录入时，静默本身成为值得关注的信息。
- 在开场白中标注「这是连续第 N 天了」
- 在善意提醒区块中点出「你连续 N 天没和系统互动了」，并附上积压的待办提醒
- 连续 3 天静默 → 情绪教练评价中标记备注为「可能处于长假/出差/健康状态，需留意回归信号」
- 连续 7 天静默 → 惊奇度扫描应触发模式变更提醒（用户使用习惯已发生结构性改变）
