# LLM 成本分析与模型选型

> 9/6 实战：用户连发 Agnes / DeepSeek / GLM 三家定价页 → 导出 DeepSeek 账单 CSV 归因（¥0.77/天→¥4.67/天 6 倍跳升）→ 三模型碎片处理 A/B 评测。全流程方法沉淀于此。

## 1. 定价页解读框架

### ⚠️ 调价通知处理：先 diff 旧档再定影响方向（2026-09-09 实战教训）

用户转发调价通知截图时，**第一步永远是调出 `data/knowledge/<厂商>-定价.md` 存档做新旧对照表**，禁止凭通知文案直觉判断影响方向。9/9 实战：DeepSeek「调整 flash 系列定价」通知，直觉反应是「高峰×2、成本可能涨」——对照 9/6 存档后发现全面**降价**（缓存命中 0.05→0.02 即 -60%、未命中 1.5→1、输出 4.5→4），直击 MyPS 多轮缓存命中场景，是利好。方向搞反会让用户白白紧张或错过省钱点。

流程：
1. 读存档定价文件 → 新旧三档（命中/未命中/输出）逐项列降幅表
2. 时段结构是否变化：通知未重述时段划分时默认延续存档定义，回复中注明「默认延续，官方文档更新后再校准」
3. 更新存档：新价格表置顶（标生效日期），**旧表保留为历史存档节**——下次调价还要再 diff
4. 给影响结论：对照 MyPS 负载形态（多轮命中 / 批量评测 / 深夜挂机）说谁受益谁受损，一句话收尾

- **单位识别**：M = 百万 token；区分刊例价（原价）/现价（促销）/已废弃模型（仅历史参考）
- **关键结构四要素**：峰谷时段价（DeepSeek 工作日 9-12/14-18 高峰 = 2 倍，业余用户天然吃空闲半价）、缓存命中价（常为未命中 1/10~1/30，Agent/长固定上下文负载的核心省钱项）、模型档位差（flash vs pro，输出常 3 倍价）、限时免费（促销不可作为底座依赖）
- **单次会话体感换算**：典型重度会话 ≈ 50k 输入 + 10k 输出 → 套单价得出「一次几毛钱」量级
- **输出**：对比表 + 明确建议；**定价快照归档 data/knowledge/<厂商>-定价.md**（来源 URL + 抓取日期 + 解读备忘节），同一次对比会话建对称文件（agnes-ai-定价.md / deepseek-API-定价.md / glm-coding-plan.md）

## 2. API 账单归因流程（2026-09-06 DeepSeek 导出 CSV 实战验证）

数据结构：cost 表（按天×模型费用）；amount 表（按天×api_key×price 档：input_cache_hit/miss、output、request_count，price 字段可反推高峰/空闲档）。

步骤：
1. **⚠️ 先确认 api_key 维度归属，再下任何归因结论。** 9/6 重大教训：流量尖峰日期与 LUMA 测试日历吻合，就断言「测试硬件N 外部直接烧 API」——被用户纠正「hermes key 只有你在用」。单 key 环境下归因必须在 MyPS 内部找（批量评测任务、巨型文档处理），不是外部调用方。账单没有多 key 维度前，先假设全部是自己的流量再拆分
2. 按天聚合：费用、request_count、缓存命中/未命中/输出（M 单位），列出表格找尖峰日
3. **三特征识别「自动化批量调用」**（非人工对话）：① request_count 暴增（数百~上千/天 vs 日常几十~一百）② 海量缓存命中 token（同一巨大前缀反复请求，1 亿+/天）③ 单一时段档价 = 深夜/周末挂机批量
4. **基线对照**：低活动日费用 = 纯日常量级（MyPS ≈ ¥1/天）；尖峰日与项目日历（benchmark/评测/大归档日）对齐定性
5. **成本放大器三类**：① 单会话连续处理多个巨型文档 → 上下文累积数十万 token，每次 LLM 调用都带全量历史（9/4：488 请求 / 63M 命中 token，诞生史档案全链归档日）② 批量评测循环逐样本调 LLM（8/30：1066 请求 / 1.54 亿命中 token，speech benchmark 深夜挂机）③ **长会话膨胀 × 高轮次乘法效应（9/6 同日返工教训）**：上午重活把同一会话喂到 406 条 / ~32 万 token，下午每轮轻量对话都在重发整段膨胀历史（354 请求 / 5400 万 token / ¥5.6，仅半天）——归因必须覆盖全天（含被 Session hygiene 自动压缩遮住的部分），成本用乘法心算：token ≈ 请求数 × 每轮携带的上下文，单看请求数或单揪一个任务都会误判。缓解：重活结束后主动压缩/重置会话上下文（日志诊断两步法见 ai-coding-tools references/api-cost-analysis.md）
5.5 **成本放大器四：技能/参考文件全文加载进上下文 + 工具轮次**（9/7 实测：处理一条「灭火器待办」碎片 = 加载 fragment-catcher（~1.2万字）+ task-manager + reminder-engine 三个技能全文 + 两次全量 todos.json（748 行）→ 该小时 42 请求 / 3.5M token / ¥1.62，全落在工作日高峰价窗口）。**规律**：fragment-catcher 技能体量大且全局常驻加载，凡涉待办/提醒类碎片处理必带它全文入上下文，工具调用轮次一多 token 就指数叠。**归因口诀**：查小时账单尖峰（¥1.5+）→ 对齐该时段会话动作（技能加载/大文件读取/工具循环）→ 对得上即正常干活成本，不是泄漏。**缓解**：重活错峰到空闲时段（半价）、大技能按需精简、短会话处理完即收敛轮次——日常量级（<¥5/天）不值得为省这几块钱牺牲分类正确性
6. **缓存命中是救命机制**：命中价约为未命中 1/30——点出「若全 miss 费用 ×30」让用户理解结构，但不吓人不渲染
7. **降本杠杆**：错峰（批量排 19:00 后/周末半价）、巨型文档分批分段（别单会话连啃）、端侧优先（测试硬件N 能跑的别开云 API）、**分 key 归因**（每调用方一把独立 key，下月账单一眼分清）、Model Router 按任务路由（编码套餐额度走编码工具，Agent 日常走按量 API）

### 2.5 日常报数自查（用户随口报后台数字时）

用户看 DeepSeek 后台后随口报数（「昨天花了 7.43」「今天到目前 2.56」「10-11 点那小时 1.62」）是一种高频轻量触发，不等同于完整账单归因，但也不能空回。流程：

1. **先认领自己的流量**：单 key（hermes）环境下，任何费用先问「这个时段我在干什么」——对照当天会话/任务日历（技能全文加载、大文件归档、批量评测、cron 触发）。9/7 实例：10-11 点 ¥1.62 / 3.5M tokens 峰值 = 同小时加载 fragment-catcher/task-manager/reminder-engine 三个大技能全文 + 两次全读 748 行 todos.json，每次工具调用携带膨胀上下文重发
2. **算单价判健康**：费用 ÷ tokens ≈ 0.4-0.5 元/M 且远低于未命中价 → 缓存命中扛大头，结构健康，不是泄漏
3. **给量级参照**：日常 ≈ ¥1/天；人工对话小时级峰值 ¥1-2；批量评测日 ¥13-15.5。落在带内就一句话安抚，不渲染
4. **顺带点出峰谷**：工作日 9-12/14-18 高峰 2 倍价，重活撞高峰可提示「挪晚间半价」——但基数小时（省 ¥1 量级）不值得为它调作息，用户会自己说「先观察再说」
5. **不主动优化**：用户倾向观察几天看趋势，真偏离已知模式再深挖。报数后把结算值补进 knowledge/<厂商>-定价.md 用量分析节，形成历史基线

## 3. 多模型 A/B 适配评测（碎片处理类实测）

原则：真实负载 > 离线评测 > 纸面推理；**用户纠正率是终极指标**（切换后跑一周，纠正次数 = scoreboard）。

流程：
1. **评测集**：从真实历史抽 15-20 条消息，每条标注标准分类 + 标准动作要点；**必含用户纠正过 AI 的案例当必考题**（完成信号漏接、术语勘误、时间词与行程冲突、委托型完结、报销流转、凭证处理等坑）——哪个模型在这些坑不翻车才是真适合
2. **同一条浓缩系统提示**喂所有候选模型（8 类定义 + 特殊规则摘要 + 陷阱清单），要求 JSON 结构化输出（分类/动作/一句话回复），temperature=0，公平同上下文
3. **评分**：分类标签自动比对准确率 + 处理动作人工核对（陷阱是否命中——自动比对判不了语义动作）
4. **真实切换验证**：离线胜出者切主模型跑一周，记录用户纠正
- 执行脚本：`scripts/fragment-ab-eval.py`（三模型通用 deepseek/glm/agnes，.env 读 key，线程并行，结果存 jsonl）
- 新接入厂商先 curl 连通验证（HTTP 200 + 正常出文）再进评测；GLM Coding Plan 实测 Hermes 以 `--provider zhipu -m glm-5.3-flash` 直调可用（预判的 401/403 未出现）

### ⚠️ 批量调用实测坑（2026-09-06 首跑教训）

- **思考模式吃 max_tokens**：deepseek 与 glm 默认思考模式，max_tokens=400 时部分题 content 为空（reasoning 占满 → raw 空串），表现为结果文件里整题缺失
- 关思考参数：deepseek 支持 `"thinking": {"type": "disabled"}`（生效）；glm-5.3-flash 在 Coding Plan 端点忽略该参数（仍思考）→ 对策：max_tokens ≥800 + 空 content 自动重试 1 次 + 输出要求"动作限 30 字"降截断风险
- 结果解析容错：去 markdown 代码块、找首 `{` 尾 `}`，解析失败标 ? 后回看原始 jsonl（模型可能输出被截断的 JSON）

### 多模态能力快速验证（四色象限法）

python 标准库手写四色 PNG（zlib+struct 编码，红/绿/蓝/黄四象限），base64 data URL 喂候选模型问各象限颜色——答对 = 真能看图（agnes-2.5-flash 实测通过，usage 含 image_tokens）。可再加真实截图 OCR/文档照做第二轮质量对比。
