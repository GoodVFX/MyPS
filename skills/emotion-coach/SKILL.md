# 情绪教练

你正在执行情绪教练任务。本 Skill 由 daily-review 在晚间总结时内部调用，不直接对用户触发。以下是完整的分析规则。

---

## 调用流程

```
daily-review 收集完今日数据
  │
  ▼
调用 emotion-coach
  │
  ├─ 输入：今日所有碎碎念内容
  ├─ 附加输入：memory/mood-trends.md 近期记录
  │
  ├─ 步骤 1：情绪信号识别
  ├─ 步骤 2：趋势判断（vs 近期基线）
  ├─ 步骤 3：生成个性化评价
  └─ 步骤 4：写入当日情绪评估到 mood-trends.md
  │
  ▼
返回评价文本 → daily-review 融入总结末尾
```

---

## 调用流程实际笔记

**已验证模式**：当 daily-review 的 steps 0.5/0.6 检测到前一轮 mood-trends 写失败时，本轮 emotion-coach 正常执行全部流程（包括步骤 4 写入）。无需因为前一轮缺失而回填——缺乏上下文的数据生成的评估是空洞的。

---

## 步骤 1：情绪信号识别

扫描今日所有碎碎念，识别以下情绪信号：

| 情绪 | 识别信号（词语/表达模式） |
|------|------------------------|
| 焦虑 | 「担心」「怕」「紧张」「来不及」「要死了」「烦死了」「压力」 |
| 兴奋 | 「太好了」「终于」「有意思」「很兴奋」「期待」「迫不及待」 |
| 疲惫 | 「累」「好困」「不想动」「撑」「熬」 |
| 平静 | 中性陈述为主，无强烈情绪词 |
| 满足 | 「不错」「开心」「满意」「挺好的」「感觉很好」 |
| 纠结 | 「不知道该」「犹豫」「到底要不要」「算了又想」 |

**判断规则**：
- 一天中可能存在多种情绪信号，取**主导情绪**
- 如果有明显的时间段变化（上午兴奋、晚上焦虑），都记录
- 如果没有明确的情绪信号 → 标记为「中性」

---

## 步骤 2：趋势判断

读取 `memory/mood-trends.md` 近 7 天的记录，对比今日情绪与近期基线。

**判断维度**：
- 今日情绪 vs 近 7 天平均：是更好、更差、还是持平？
- 是否存在连续 3 天以上的同一种负面情绪？
- 是否存在突然的情绪变化（之前平静，今天突然焦虑）？

**注意：mood-trends.md 中的条目可能不按日期排序**。条目按创建顺序追加，如果某几天的 daily-review 因系统问题未运行，日期可能出现断层。读取近 7 天记录时，**必须按日期提取并排序**，而非简单取文件末尾 N 条。示例伪代码：
```
所有条目 → 按 `### YYYY-MM-DD` 提取日期 → 排序 → 取最近 7 天
```

**输出**：一句话趋势判断，供步骤 3 使用。

---

## 步骤 3：生成个性化评价

基于步骤 1 和 2 的结果，生成一段简短的情绪评价。

### 评价原则

1. **基于实际内容**：引用今日碎碎念中的具体内容，不做泛泛的评价
2. **温和鼓励**：如果今天状态不好，给一句有温度的话，但不说教
3. **不过度解读**：一两句碎碎念不构成情绪判断，需要多个信号支撑
4. **不用模板**：不写「今天辛苦了」「明天会更好」「加油」
5. **简短**：3-5 句话足够

### 不同场景的示例

**状态不错的一天**：
```
今天整体状态不错——下午跑步那段能感觉出心情挺好。
有产出也有休息，节奏健康。保持就好。
```

**焦虑的一天**：
```
今天焦虑信号比较明显——客户方案、截止日期、加上晚上的碎碎念提到的压力。
这些事都有具体的解决办法，不用同时想全部。明天从最急的那个开始。
```

**平淡的一天**：
```
今天情绪比较平稳，没什么大起大落。
普通的一天也是好的一天。晚上早点休息。
```

**疲惫的一天**：
```
今天挺累的，碎碎念里两次提到累。
如果没什么必须今晚做的事，就别硬撑了。明天状态会好一些。
```

**零交互日（用户全天未与系统互动）**：

先确认今日是星期几（`datetime.datetime.today().weekday()`），区分周末 vs 工作日。**再检查 todos.json 中是否有行程类 deadline 覆盖今日**（如「山海关看姐姐 8/4-8/6」「云南旅游 8/11-8/16」）——已知行程期间的零录入属于预期行为，直接按「外出节奏」评价，不套用工作日的「可能忙碌」表述，也不标记为异常静默。

- **周末/假日（周六、周日、已知假日）**：
  ```
  今天很安静。周日（休息日），正常的休息节奏。
  ```
  语气放松，不做「可能是在外出」的推测——日期已知是休息日，将括号中的星期几替换为实际值。

- **工作日（周一至周五，且非假日）**：
  ```
  今天很安静，工作日但没有录入内容。
  可能是忙碌的一天。没有数据也是一种状态。
  ```
  语气中性，不附带评判。连续 2 天以上才触发「连续零交互日」处理。

**连续零交互日（2 天及以上未与系统互动）**：
```
今天依然安静。连续第 N 天没有录入。
如果是在休假或外出，好好放松。之前积压的几件事还在——回来再看也不迟。
```
连续零交互日的备注中应标注「连续第 N 天零录入」，并在趋势判断中说明此模式是否属于正常范围（如周末 vs 工作日）。
连续 3 天以上 → 备注补充「可能处于长假/出差/健康状态，留意回归信号」。
连续 7 天以上 → 强度标记为「中」，因为使用模式已发生结构性改变。

**行程覆盖的连续静默（2026-08-05 实测）**：已知行程（todos.json 中有日期区间的行程类 deadline）覆盖的连续零录入日仍计入「连续第 N 天」的累计，但评价框架为「外出节奏」而非「静默异常」——如「连续第 2 天没有录入，但你在山海关的行程中，这是正常的探亲节奏」。行程结束后仍未回归才触发「留意回归信号」备注。

### 步骤 4：写入情绪评估

将当日情绪评估结果追加到 `memory/mood-trends.md`。

**格式**：

```markdown
### YYYY-MM-DD 情绪评估
- **主要情绪**：[焦虑/兴奋/疲惫/平静/满足/纠结/中性]
- **信号来源**：[今日碎碎念中的情绪线索简述]
- **强度**：[低/中/高]
- **备注**：[特别观察，如与某事件相关]
```

**备注中的锻炼断档计数约定**：备注末尾维护「无锻炼记录（连续第 N 天）」，N 继承自最近一条记录的计数 +1；当日有明确锻炼记录（见 daily-review 锻炼检测）则重置或省略。该计数由 daily-review 引用，用于「锻炼一个多月没记录了」这类温和提醒（2026-08-09 实测：从 8/8 的「连续第 28 天」顺延为「连续第 29 天」）。

**实际文件结构**：

```markdown
# 情绪趋势

> ...（说明文字）

## 情绪记录

### 2026-06-07 情绪评估
- **主要情绪**：...
- **备注**：...

### 2026-06-12 情绪评估
- **主要情绪**：...
- **备注**：...（文件末尾）
```

所有条目统一为 `### YYYY-MM-DD 情绪评估` 格式，条目间用空行隔开。文件末尾有一个 `---` 分隔线，之后是文档说明区块（`### 这个文件怎么用`、`### 和其他文件的关系` 等）——这是模板自带的固定结构，不是被修改过的痕迹。

**写入前检查（防重跑重复）**：读取 `memory/mood-trends.md`，搜索 `### YYYY-MM-DD 情绪评估`（替换为今日日期）。
- **已存在** → 跳过写入。前一轮已成功记录今日评估，重复写入会产生重复条目。由 daily-review 的步骤 0.5 负责检测并跳过本步骤，本步骤不主动跳过——调用方（daily-review）应通过步骤 0.5 的判断决定是否调用本步骤。

**写入技巧**（承接上方格式说明，本步骤内唯一写入流程区块）：
- 如果 mood-trends.md 尚处于初始化状态（含有 `（暂无）` 占位符），用 `patch` 替换该占位符为首条记录
- 如果已有历史记录（一般情况），有两种已验证的方案可供选择：

  **方案 A（推荐——最安全）**：匹配最后一条记录的**完整区块**，整体替换后再追加新条目。
  ```
  1. read_file("~/.hermes/memory/mood-trends.md") → 定位最后一条记录
  2. 复制该条记录的精确全文作为 old_string
     （从「### YYYY-MM-DD 情绪评估」到最后一个「- **备注**：」行的完整内容）
  3. new_string = old_string + "\n\n" + "### 新日期 情绪评估\n..."（新条目全文）
  4. patch(old_string=精确全文, new_string=新全文)
  ```
  **原理**：patch 替换的是匹配到的整段文本。old_string 覆盖整个旧条目时，旧内容被一同移除，不会产生残留。read_file 确保你用的是文件的精确文本（而非凭记忆写的近似文本）。

  **方案 B（备选——更简洁，适合文件结构稳定时使用）**：匹配文档说明区的唯一标题作为锚点，在其之前插入新条目。
  ```
  1. old_string = "### 这个文件怎么用"
  2. new_string = "---\n\n### 新日期 情绪评估\n- **主要情绪**：...\n- **信号来源**：...\n- **强度**：...\n- **备注**：...\n\n---\n\n### 这个文件怎么用"
  3. patch(old_string=锚点, new_string=带新条目的锚点)
  ```
  **优势**：不需要复制旧条目内容，new_string 更短，无拷贝错误风险。
  **限制**：依赖 `### 这个文件怎么用` 在文件中唯一且存在。如果该标题被修改，方案 B 失效。

  **方案 B 陷阱（重要）**：old_string **不要包含 `---\n\n` 前缀**。虽然 `---\n\n### 这个文件怎么用` 看起来更精确，但实际上 `---\n\n###` 模式在文件中出现了多次（每个条目之间都有 `---` 分隔线），patch 的模糊匹配策略会找到大量候选，导致匹配失败。应只使用 `### 这个文件怎么用` 作为唯一锚点——该标题在文件中只出现一次。new_string 中的 `---\n\n` 作为新条目的前缀由你自己提供。

  **方案 C（不推荐——已知陷阱）**：仅匹配标题行，在 new_string 中重建旧条目。经 2026-07-07 实战验证，此方案因 patch 只替换匹配行（标题行），旧条目的内容行留在原位，导致新旧内容重复。改用方案 A 或 B。
- 写入前**必须** `read_file` 确认最后几条记录的内容和行号，确保不会误匹配历史条目
- 不需要用户确认（属于工作记忆层）

**写入陷阱（重要）**：
- `patch` 替换的是 **old_string 精确匹配到的文本**，不涉及匹配范围外的行。所以 old_string 必须覆盖你想替换的全部内容——如果只想追加而非替换，使用方案 B。
- **不要用 `- **备注**：` 行作为主要锚点**。patch 的模糊匹配策略可能将一条记录的备注行误匹配到另一条结构相似但内容不同的备注行（比如匹配到更早的条目），导致意外替换历史数据。方案 A 使用完整区块避免了此问题，方案 B 使用唯一标题行也避免了此问题。
- **不要使用 `---\n\n## 使用说明` 作为锚点**——这个结构在 mood-trends.md 中不存在，会导致 patch 失败。
- 写入后**必须**立即 `read_file` 验证两件事：①旧条目未被意外删除或损坏 ②新条目出现在预期位置。如果旧条目还存在（方案 A 应为空），说明方案 B 才是正确选择，或锚点不唯一。
- **读取工具必须用 `read_file`（而非 execute_code 的 `open()`）**：patch 工具通过 read_file 工具调用来跟踪「文件已读」状态。若用 execute_code 读取后直接 patch，会触发 patch 警告「文件被 sibling subagent 修改但本 agent 从未读取」（2026-07-31 实测，警告无害、写入成功）。该警告说明文件读取未被工具跟踪，存在覆盖并行改动而不自知的风险。正确流程：read_file → patch → 验证（验证步骤见下方代码范例，不可省略）。

**验证代码范例**（在 patch 之后立即执行）：
```python
# 验证 TWO things: old entries preserved + new entry inserted
content = open(os.path.expanduser("~/.hermes/memory/mood-trends.md")).read()
yesterday = "YYYY-MM-DD"  # replace with yesterday's date
today = "YYYY-MM-DD"      # replace with today's date
old_ok = f"### {yesterday} 情绪评估" in content
new_ok = f"### {today} 情绪评估" in content
if old_ok and new_ok:
    print("✅ mood-trends 写入验证通过：旧条目保留，新条目已插入")
elif old_ok and not new_ok:
    print("❌ 新条目未出现在 mood-trends.md 中，需重试")
    # 重试逻辑：重新执行一次方案 B 或 A
elif not old_ok and new_ok:
    print("⚠️ 旧条目被意外覆盖！新条目已写入但历史数据丢失，需恢复")
    # 恢复逻辑：用历史条目重建
else:
    print("❌ 两者都失败，文件可能被损坏")
```

- 如果发现意外替换了历史数据：立即用 `read_file` 读取当前内容，然后 `patch` 恢复丢失的条目，写入顺序无关紧要。恢复时用 `### YYYY-MM-DD 情绪评估` 标题行作为唯一锚点——从 read_file 输出中复制精确文本作为 old_string。

## 重要约束

- 情绪教练**不直接触发善意提醒**。如果发现连续多天的负面情绪，只是将信号传递给 daily-review，由 daily-review 决定是否在善意提醒区块中提及
- 情绪评估**不需要用户逐条确认**（属于工作记忆层），但个性化评价的措辞应保持温和克制
- 如果用户明确不想要情绪评价 → 可通过修改 USER.md 的碎片处理规则来关闭本 Skill
