# 外部项目调研与借鉴分析

用户是 AI 深度实践者，做 长期项目X（陪伴机器人/在场体）需要持续调研竞品和参考项目（历史：竞品A、竞品B、竞品C）。本 skill 定义该类任务的完整流程。

---

## 处理流程

1. **抓主页 README**：web_extract GitHub 仓库页——标题、简介、核心亮点、License 一次拿到
2. **抓完整代码树**：GitHub API `https://api.github.com/repos/{owner}/{repo}/git/trees/{branch}?recursive=1`
   - 分支不确定时 main 和 master 各试一次（404 就换）
   - API 返回完整文件清单，比网页抓取结构化，能定位关键模块和文件大小
3. **定位关键模块**：根据用户关注点找对应目录（如「情绪系统」→ 看 agent/、otto/、emotion 相关）。⚠️ 别预设结构——功能可能是「LLM 输出 + 动作库」而非独立模块（竞品C 情绪系统实为 agent loop 输出 + otto_movements 原语库，无独立 emotion 模块）
4. **需要细节时抓源码**：`https://raw.githubusercontent.com/{owner}/{repo}/{branch}/{path}` 直接拿关键文件
5. **检查 License**：非商业许可（CC BY-NC-SA 等）只能抄理念，不能抄代码/硬件做商业化——回复里必须提醒
6. **提炼借鉴点并映射用户项目**：每个借鉴点落到 长期项目X 的具体层（Memory/Realtime/Execution/情绪/交互）。用户思维模式「先具象后抽象」：先说它长什么样/怎么实现，再说理念层面的启发
7. **存档**：knowledge/ 建主题文件（如 `ottoclaw-借鉴分析.md`），结构：项目定性 → 架构要点 → 借鉴点（映射 长期项目X）→ 注意 → 连接点。连接点同时挂到相关项目文件（如 luma-design.md 的「连接点」区块）——双入口保证未来翻得到
8. **回复结构**：一句话定性 → 核心借鉴点（映射 长期项目X）→ 注意点 → 提议是否深扒

## 模型/技术选型评估（扩展场景）

用户问「XX 新模型/新技术我们能用来做 长期项目X 吗」时，走五维评估框架（2026-08-09 LFM2.5-2.6B 实战，存档见 knowledge/luma-kata-local-llm-analysis.md 第七节）：

1. **基本规格**：参数规模、架构、上下文、量化体积、官方速度（tok/s）——先回答「它是什么」
2. **许可证（先于技术适配查）**：商用门槛是硬约束——收入上限（如 LFM Open License 年收入 <1000 万美元免费商用）、非商业限制；对比同赛道宽松许可（Apache 2.0 / MIT）给用户选择全景。个人/小团队阶段通常都合规，但要写清边界和未来风险
3. **场景匹配**：映射 长期项目X 的层（Memory/Realtime/Execution/LLM 插件位）——是否专项适配 agent harness、本地推理收益（零 token 成本、数据不出设备）、能否做本地默认大脑 + 云端 API 增强
4. **已知局限**：多模态缺失、官方明说不擅长的任务域、推理延迟特征——诚实列出，别被亮点话术带偏；与既往判定（如「2B 做不了陪伴」）的关系要标注为待实测验证而非直接推翻
5. **实测计划**：落到具体硬件（如 测试硬件N）的验证项：量化版本、真实 tok/s、工具调用、中文质量、首 token 延迟——数据说话再定是否采用

存档：追加到对应 knowledge 主题文件，不新建碎片文件；回复先给结论（能用/不能用+理由），再列关键数据。

### HF 模型系列评估（多模型发布者）

用户发 HF 上某发布者的模型系列（如「audio8 发布了 ASR/TTS 一堆小模型」）时，流程与单模型评估不同——先系列后逐个。详细 checklist 见 references/hf-model-evaluation.md。核心要点：

1. **先抓发布者组织主页**（huggingface.co/{user}）拿全谱系：一个团队常发多个模型，许可证各不相同，不能因一个模型宽松就默认全系列可商用（Audio8 实战：ASR-0.1B 是 CC-BY-NC 非商用，同系列其他模型 Apache 2.0）
2. **逐模型核对许可证**——NC 许可证直接标「出局/仅开发参考」，回复里明确点名（用户有产品化视角，这个坑必须提前踩）
3. **语音模型额外维度**：语言覆盖（含中文？）、zero-shot 克隆（TTS 人设音色）、流式 PCM 支持、自带神经 codec、ASR 热词提升（人名/专有词纠偏）
4. **CPU 实时率（RTF）是端侧语音最大未知数**：官方常只给 GPU（RTFx）和内存数据，测试硬件N 纯 CPU 的 RTF 没人测——识别这个未知数并列为实测第一项，不能拍板采用
5. **评测可信度分级**：标准榜单（Open ASR Leaderboard 统一流程）> 团队自报内部评测；中文 CER 数据尤其要标注来源
6. **团队可信度信号**：arXiv 论文、社区数据（likes/followers）、部署路径完备度（ONNX/vLLM/SGLang/MLX 多形态）

### 用户拍板「加入测试」后的落盘闭环（2026-08-10 Audio8 实战）

评估完用户说「可以加入测试计划」时，不只是确认——走闭环：

1. **建测试计划文件**：knowledge/luma-model-benchmark-plan.md——时间线、测试对象表（模型/规格/许可证/测什么）、判断线（对话 LLM ≥10 tok/s 可用 ≥15 流畅；中文 ASR CER ≤8% 可用 ≤5% 良好、RTF<0.5；TTS RTF<1 实时 <0.5 舒适）、资源竞争测试（LLM+ASR+TTS 同跑，Supervisor 多进程）、语料准备、结论输出格式
2. **更新既有待办**：合并进已有 长期项目X 开发启动条目（dl-030），不新建重复条目
3. **更新既有 cron 提醒**：cronjob update 把新测试项并进已排好的提醒 prompt（如 8/17 reminder-luma-dev-start），不删不新建——用户习惯「回来后一起开干」的时间锚点
4. **三处归档**：diary + events + 测试计划文件各一条；评估结论已在当轮入 luma-design.md 端侧模型选型参考
5. 回复给测试计划要点摘要，并承诺「语料和测试清单实测前备好」——用户回来后直接开跑

## 教学项目变身模式（2026-08-10 pi-from-scratch 实战）

用户发来的项目可能不是「可借鉴的竞品/参考」，而是**教学项目**（README 定位为教程/「从 0 手写」/「一篇文章」），用户可能进一步要求「变身成这个项目，通过对话对我教学」。识别信号：README 出现「教学」「从 0 写出」「这是一篇文章」、配套教学网站、代码随文章渐进补全。

**处理流程**：
1. **完整抓取**：README + 全部 docs/ + 全部 src/ 源码。教学项目的价值在文章（拆解思路）和源码（最小实现）两者，缺一不可——只抓 README 会丢掉教学核心
2. **归档为课程文件**：knowledge/ 建 `{项目名}-course.md`，结构：项目全景（定位/核心思想/原文引用）→ 模块地图（文件/职责/对应原版/长期项目X 类比表）→ 数据流（一轮走查）→ 关键设计决策（保留了什么、砍了什么、为什么）→ 课程进度（每课记录：已讲内容/比喻/映射）→ 源码存档路径 → 连接点
3. **源码存档**：knowledge/ 下建 `{项目名}-src/` 目录存核心源文件（重点存「灵魂文件」，如 agent.ts），供后续课程引用
4. **教学法**（适配用户学习风格：先具象后抽象、比喻巩固、应用构建者）：
   - 用身体/生活类比讲模块分工（llm=嘴皮子、agent=大脑、tools=手脚、tui=脸、cli=神经）
   - 每章必须映射用户长期项目（长期项目X 的 listen/speak/move 就是 tools、Context 纯 JSON 就是 Memory 层地基）——用户学任何技术都要求落到自己的项目
   - 一次一章，控制篇幅（用户在通勤/上班场景读微信）
   - 每课结尾留一个思考题（把「A 是不是 B？」类开放问题抛给用户，下一课对答案）
   - 课程进度写回 course.md，保证跨会话续课

**与普通调研的区别**：普通调研输出「借鉴点+注意+提议深扒」就完事；教学模式输出是一系列课程，持续性、进度记录、互动性是关键。识别到是教学项目后默认问一句「要我直接带你学，还是先存档」——用户常直接要教学（本次：用户主动提出变身教学）。

## 延后深扒模式

用户说「先记上，回头再扒」「分析到这吧」时——柔性延后，不建待办/不设 Cron：

1. 在 knowledge 主题文件追加「后续安排」区块：状态 + 触发条件 + 深扒目标清单
2. 触发条件通常绑定 长期项目X 进展阶段（如「Execution 层/情绪模块设计进展到类似程度时」），不绑定日期
3. 连接点已挂到项目文件，触发时自然翻得到
4. 回复确认一句「已记，到时候说一声我直接扒」

## 输出要求

- 借鉴点必须映射到用户项目，不堆理论（用户是应用构建者不是研究员）
- 诚实标注项目局限（如「ESP32 玩具级，摄像头未启用」），别被亮点话术带偏
- 深扒提议给具体目标（哪个文件、哪部分），让用户一句话就能点头

## 已验证工具链

- GitHub 仓库页：web_extract 直接抓，README 摘要有效但长文会被截断——细节靠代码树 API 补
- 代码树：git/trees API 一次性拿全量文件（含 size），比逐目录 contents API 高效；web_extract 对 api.github.com 的 JSON 可能失败，用 curl 兜底
- raw.githubusercontent.com：抓单文件源码，无需 API token
- 2026-08-08 实战：竞品C 分析全流程走通，4 次 web_extract 完成「README + 全量代码树 + 关键目录 + 定位」

### ⚠️ 网络波动下的 GitHub 抓取降级路径（2026-08-10 实战）

抓取整仓库时按序尝试，别在一个方法上死磕：

1. `git clone --depth 1`（快则首选）→ 超时/卡死则放弃，别等
2. codeload tarball（`https://codeload.github.com/{owner}/{repo}/tar.gz/refs/heads/main`）→ 也可能超时
3. raw 直连逐文件 `curl`（单文件 2 秒成功过，但间歇性波动：同一文件几分钟后连超 60 秒）
4. **web_extract 抓 raw URL 最稳**——走服务端抓取，绕过本地到 GitHub 的波动链路；小文件返回全文，大文件（30KB+）给 LLM 摘要仍可用；一次最多 5 个 URL

经验：网络波动场景下别用后台脚本批量下载（后台进程全军覆没、每个文件空等 60 秒超时），改前台小批量（3-5 个）+ 短超时（25-30s）+ 失败的换 web_extract。下载到 /tmp 的内容要立刻复制到 knowledge/ 存档——/tmp 会丢。

## Pitfalls

- README 声称的功能（如「22 种情绪」）与代码结构可能不一致——以代码树核实为准
- 别在一个目录内容 API 上逐个爬（慢），trees?recursive=1 一次拿全
- 存档文件名用「项目名-分析」格式，便于和竞品文件（luma-competitors.md）区分——参考项目 vs 直接竞品分开存
