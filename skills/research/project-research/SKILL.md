# 外部项目调研与借鉴分析

用户是 AI 深度实践者，做 长期项目X（陪伴机器人/在场体）需要持续调研竞品和参考项目（历史：竞品A、竞品B-esp32-server、竞品C）。本 skill 定义该类任务的完整流程。

> 个人 agent 赛道竞品（Grok Bot 等 always-on agent）的坐标与对比结论 → `references/个人agent竞品坐标-grok-bot-202609.md`（与 长期项目X 硬件竞品分开归档）

---

## 处理流程

1. **抓主页 README**：web_extract GitHub 仓库页——标题、简介、核心亮点、License 一次拿到
2. **抓完整代码树**：GitHub API `https://api.github.com/repos/{owner}/{repo}/git/trees/{branch}?recursive=1`
   - 分支不确定时 main 和 master 各试一次（404 就换）
   - API 返回完整文件清单，比网页抓取结构化，能定位关键模块和文件大小
3. **定位关键模块**：根据用户关注点找对应目录（如「情绪系统」→ 看 agent/、otto/、emotion 相关）。⚠️ 别预设结构——功能可能是「LLM 输出 + 动作库」而非独立模块（竞品C 情绪系统实为 agent loop 输出 + otto_movements 原语库，无独立 emotion 模块）
4. **需要细节时抓源码**：`https://raw.githubusercontent.com/{owner}/{repo}/{branch}/{path}` 直接拿关键文件
5. **检查 License**：非商业许可（CC BY-NC-SA 等）只能抄理念，不能抄代码/硬件做商业化——回复里必须提醒
6. **提炼借鉴点并映射用户项目**：每个借鉴点落到 长期项目X 的具体层（Memory/Realtime/Execution/情绪/交互）。用户思维模式「先具象后抽象」：先说它长什么样/怎么实现，再说理念层面的启发。⚠️ 映射目标以用户当次问题为准——发 长期项目X 相关项目映射 长期项目X；发 Agent Memory/助理系统类项目时目标可能是 **MyPS 自身**（2026-09-29 实战），此时对照「我的三层架构」（memory 声明性/skills 程序性/session_search+knowledge 情景语义）找差距，结论落到「差距在自动化程度，不在有无」，并守住「理念抄、组件不引」纪律（MyPS 跑在旧手机，不引重依赖）
7. **存档**：knowledge/ 建主题文件（如 `ottoclaw-借鉴分析.md`），结构：项目定性 → 架构要点 → 借鉴点（映射 长期项目X）→ 注意 → 连接点。连接点同时挂到相关项目文件（如 projectx-design.md 的「连接点」区块）——双入口保证未来翻得到
8. **回复结构**：一句话定性 → 核心借鉴点（映射 长期项目X）→ 注意点 → 提议是否深扒

## 模型/技术选型评估（扩展场景）

用户问「XX 新模型/新技术我们能用来做 长期项目X 吗」时，走五维评估框架（2026-08-09 LFM2.5-2.6B 实战，存档见 knowledge/projectx-competitora-local-llm-analysis.md 第七节）。**分工**：本节管纸面预筛与许可审查；成本维度（定价页解读/账单归因/性价比对比）归口 tools/llm-cost-analysis；测试硬件N 实测执行归口 host-ops（见其 `references/llm-model-eval-playbook.md`）：

0. **定位先行（先于五维）**：先翻 `~/.hermes/data/knowledge/projectx-design.md` 的「端侧模型选型参考」区块确认既有格局（端侧主脑=Gemma4-E2B，ASR/TTS 各有甜点位），再判定新模型归属哪一层——主脑 / ASR / TTS / 反射层·执行层 / 记忆 embedding。超小模型（<100M）永远不是主脑候选，评估对象是「能当哪个器官」（2026-09-22 Needle 3 实战：定位=执行层反射路径，非主脑）。结论必须显式写明「不改变既有选型/不新开战线」或「动了 XX 决策」——守门员纪律，冻结线除非新事实不重开
0. **先核对档案现状（2026-09-22 教训）**：引用既有选型/评测结论前，确认该主题有无后置的冻结/裁定文档——知识库里「中间轮结论」可能已被 final validation 或 GPT 裁定翻盘，别拿中间结论当现行事实。实例：凭 projectx-design.md 8/28 补测条目说「Gemma4-E2B 当选主脑」，被用户纠正「主脑不是千问吗」；8/30 冻结文档实为 Qwen3.5-2B，Gemma 仅回退。修复姿势：选型档案区补冻结+裁定条目，旧中间条目标注「以 X 为准」
1. **基本规格**：参数规模、架构、上下文、量化体积、官方速度（tok/s）——先回答「它是什么」。附**平台前置门**：测试硬件N 是 x86_64，必须核对官方是否出 linux-x86_64 引擎/二进制（端侧项目常只发 macos-arm64/linux-arm64，官方 supported-devices/平台页是权威来源；Needle 3 有明确 linux-x86_64 文件夹。ARM-only → 测试硬件N 出局，只能抄理念）
2. **许可证（先于技术适配查）**：商用门槛是硬约束——收入上限（如 LFM Open License 年收入 <1000 万美元免费商用）、非商业限制；对比同赛道宽松许可（Apache 2.0 / MIT）给用户选择全景。个人/小团队阶段通常都合规，但要写清边界和未来风险
3. **场景匹配**：映射 长期项目X 的层（Memory/Realtime/Execution/LLM 插件位）——是否专项适配 agent harness、本地推理收益（零 token 成本、数据不出设备）、能否做本地默认大脑 + 云端 API 增强
4. **已知局限**：多模态缺失、官方明说不擅长的任务域、推理延迟特征——诚实列出，别被亮点话术带偏；与既往判定（如「2B 做不了陪伴」）的关系要标注为待实测验证而非直接推翻。**中文第一门**：初代/蒸馏端侧模型多英文倾向（蒸馏自英文前沿模型），中文 tool-call/意图准确率列为实测第一项，不达标一票否决
5. **实测计划**：落到具体硬件（如 测试硬件N）的验证项：量化版本、真实 tok/s、工具调用、中文质量、首 token 延迟——数据说话再定是否采用

### 引用选型结论前先核对冻结/裁定档（2026-09-22 实战）
LUMA 的选型现状以**权威冻结/裁定文档**为准，不以设计日志的最新条目为准——设计日志可能停在中间轮结论：
- 现任主脑：**Qwen3.5-2B / Q4_K_M / reasoning off**（8/30 冻结，`projectx-v1-主脑冻结-20260830.md`）。Gemma4-E2B 是回退备选——design 日志里 8/28「Gemma4-E2B 当选」为中间轮结论，两天后被 final validation 翻盘
- 选型循环：**已正式停止**（9/9 GPT 裁定，`projectx-minicpm5-2b-gpt裁定-20260909.md`）。LUMA 原则：新模型须同硬件、同 Runtime、同 Benchmark、系统级击败现任才可替换主脑
- 实战教训：评估 Needle 时凭 projectx-design.md 的 8/28 条目说「主脑是 Gemma」，被用户纠正「主脑不是千问吗」。凡回复要引用「现任主脑/当选结论」，先查文件名含 冻结/裁定/freeze 的权威档核对；没把握就说「我确认一下」，不给出肯定结论
- 不挑战主脑位的组件级候选（反射层/第二脑/ASR/TTS/工具路由）仍可正常评估，但结论须显式写「不碰主脑位、不违反选型冻结」，评估口径与主脑选型分开

存档：追加到对应 knowledge 主题文件，不新建碎片文件；回复先给结论（能用/不能用+理由），再列关键数据。

### HF 模型系列评估（多模型发布者）

用户发 HF 上某发布者的模型系列（如「audio8 发布了 ASR/TTS 一堆小模型」）时，流程与单模型评估不同——先系列后逐个。详细 checklist 见 references/hf-model-evaluation.md。核心要点：

1. **先抓发布者组织主页**（huggingface.co/{user}）拿全谱系：一个团队常发多个模型，许可证各不相同，不能因一个模型宽松就默认全系列可商用（Audio8 实战：ASR-0.1B 是 CC-BY-NC 非商用，同系列其他模型 Apache 2.0）
2. **逐模型核对许可证**——NC 许可证直接标「出局/仅开发参考」，回复里明确点名（用户有产品化视角，这个坑必须提前踩）
3. **语音模型额外维度**：语言覆盖（含中文？）、zero-shot 克隆（TTS 人设音色）、流式 PCM 支持、自带神经 codec、ASR 热词提升（人名/专有词纠偏）
4. **CPU 实时率（RTF）是端侧语音最大未知数**：官方常只给 GPU（RTFx）和内存数据，测试硬件N 纯 CPU 的 RTF 没人测——识别这个未知数并列为实测第一项，不能拍板采用
5. **评测可信度分级**：标准榜单（Open ASR Leaderboard 统一流程）> 团队自报内部评测；中文 CER 数据尤其要标注来源
6. **团队可信度信号**：arXiv 论文、社区数据（likes/followers）、部署路径完备度（ONNX/vLLM/SGLang/MLX 多形态）

### 用户拍板「加入测试」后的落盘闭环（2026-08-10 Audio8 实战）

评估完用户说「可以加入测试计划」时，不只是确认——走闭环：

1. **建测试计划文件**：knowledge/projectx-model-benchmark-plan.md——时间线、测试对象表（模型/规格/许可证/测什么）、判断线（对话 LLM ≥10 tok/s 可用 ≥15 流畅；中文 ASR CER ≤8% 可用 ≤5% 良好、RTF<0.5；TTS RTF<1 实时 <0.5 舒适）、资源竞争测试（LLM+ASR+TTS 同跑，Supervisor 多进程）、语料准备、结论输出格式
2. **更新既有待办**：合并进已有 长期项目X 开发启动条目（dl-030），不新建重复条目
3. **更新既有 cron 提醒**：cronjob update 把新测试项并进已排好的提醒 prompt（如 8/17 reminder-projectx-dev-start），不删不新建——用户习惯「回来后一起开干」的时间锚点
4. **三处归档**：diary + events + 测试计划文件各一条；评估结论已在当轮入 projectx-design.md 端侧模型选型参考
5. 回复给测试计划要点摘要，并承诺「语料和测试清单实测前备好」——用户回来后直接开跑

## 教学项目变身模式（2026-08-10 pi-from-scratch 实战）

用户发来的项目可能不是「可借鉴的竞品/参考」，而是**教学项目**（README 定位为教程/「从 0 手写」/「一篇文章」），用户可能进一步要求「变身成这个项目，通过对话对我教学」。识别信号：README 出现「教学」「从 0 写出」「这是一篇文章」、配套教学网站、代码随文章渐进补全。

**处理流程**：
1. **完整抓取**：README + 全部 docs/ + 全部 src/ 源码。教学项目的价值在文章（拆解思路）和源码（最小实现）两者，缺一不可——只抓 README 会丢掉教学核心
2. **归档为课程文件**：knowledge/ 建 `{项目名}-course.md`，结构：项目全景（定位/核心思想/原文引用）→ 模块地图（文件/职责/对应原版/长期项目X 类比表）→ 数据流（一轮走查）→ 关键设计决策（保留了什么、砍了什么、为什么）→ 课程进度（每课记录：已讲内容/比喻/映射）→ 源码存档路径 → 连接点
3. **源码存档**：knowledge/ 下建 `{项目名}-src/` 目录存核心源文件（重点存「灵魂文件」，如 agent.ts），供后续课程引用
4. **教学法**（适配用户学习风格：先具象后抽象、比喻巩固、应用构建者）：
   - 用身体/生活类比讲模块分工（llm=嘴皮子、agent=大脑、tools=手脚、tui=脸、cli=神经）
   - 每章必须映射用户长期项目（长期项目X 的 listen/speak/move 就是 tools、Context 纯 JSON 就是 Memory 层地基）——用户学任何技术都要求落到自己的项目
   - 一次一章，控制篇幅（用户在通勤/上班场景读微信）
   - 每课结尾留一个思考题（把「A 是不是 B？」类开放问题抛给用户，下一课对答案）
   - 课程进度写回 course.md，保证跨会话续课

**与普通调研的区别**：普通调研输出「借鉴点+注意+提议深扒」就完事；教学模式输出是一系列课程，持续性、进度记录、互动性是关键。识别到是教学项目后默认问一句「要我直接带你学，还是先存档」——用户常直接要教学（本次：用户主动提出变身教学）。

## 自用工具评估模式（2026-09-20 workbuddy-auto-signin 实战）

用户发仓库链接问「能用这个帮我做 X 吗 / 你能帮我跑吗」时，目标不是借鉴分析，是**自用部署可行性评估**。此时不要套「借鉴点映射 长期项目X」的输出要求。

**评估五问**：
1. **脚本必须在哪台机器跑？**——找运行位置的硬约束：读什么凭据/数据文件、依赖哪台机器的登录态（实例：signin 脚本读 某第三方AI助手 客户端本机凭据文件 → 必须跑在装客户端的机器上，MyPS 主机没有凭据=不可托管）
2. **我有无执行通道？**——本机可跑 / 远程 SSH 可达 / 只能用户自己跑。SMB 只读共享不等于能执行命令
3. **托管 vs 用户本机跑的权衡**——凭证拉到 MyPS 主机=token 出机有安全面+客户端更新后失效；用户本机跑=需要用户动手。默认推荐用户本机方案，除非用户主动愿意托管
4. **维护风险**——逆向 API 随上游更新失效？账号行为风险？一句带过不夸大
5. **给出可直接粘贴的指令**——懒人一键法（如粘给目标工具自己设置）+ 推荐法（系统级安装），用户一句话就能动手

**输出结构**：能用+机制一句话 → 路径选项（含推荐及理由）→ 我能/不能代办及为什么 → 风险注意。

## 批量调研模式（2026-09-29 十个 Agent Memory 项目实战）

用户一次发来 N 个项目（文章清单/榜单）要求「理解分析机理+启示」时的变体流程：

1. **批量抓取**：execute_code 循环 web_extract（每次最多 5 URL，10 个项目两批搞定），预览截断到 ~2800 字符防 stdout 超限，不要逐个开请求
2. **数字必核实**：文章/榜单的 stars、定位描述逐个用 GitHub API 复核（terminal for 循环 curl api.github.com/repos/$r 一轮拿全）——实战发现文章 OpenMemory 描述整体过时（旧版已入 archive、仓库已转型、仅 73 stars），Hindsight 实际 40.9K。勘误集中列一节，这是「多走一步」的直接证据
3. **全景先于逐项**：N>3 时先给三轴分类全景表（本项目例：怎么存/怎么进化/怎么验证），让用户先见地图再见树；然后逐项机理速览（stars 用核实值并注日期）
4. **启示按「借鉴什么→升级前后对比」粒度写**：用户必然追问「哪些可以借鉴、有什么提升、讲具体一些」——第一轮分析就按此粒度落（痛点→升级后→量化提升），省一轮往返
5. **归档**：N 个项目合一档 `主题-十项目-机理与启示-YYYYMM.md`，含全景表+逐项机理+文章勘误+启示映射+不做清单；不建 N 个碎片文件

## 竞品官方文档站阅读模式（2026-09-30 某AI通道服务 docs 实战）

用户发竞品官方文档链接（如 lightvela.com/docs/overview）要求「了解其完整功能」时：

1. **先抓 overview/入口页**，从页尾「下一步/相关链接」拿到子页清单，再一批 web_extract（≤5 URL/次）读核心子页（核心概念/配置总览/快速开始/定价公告）——入口页只是目录，读完子页才算「了解完整功能」
2. **「建设中/即将上线/roadmap」区块是金矿**：官方公告自己承认没做完的能力（某AI通道服务 付费公告承认「自动任务」「记忆管理界面」「文件管理」建设中）= 竞品分析里最诚实的软肋清单，直接映射到对比框架的考点——它 roadmap 里的 = 我们已上线跑的，是「同引擎、养育不同」的活例证
3. **文档内部口径互查**：营销页/overview/FAQ/公告对同一事实的数字常不一致（官网「10 秒极速开通」vs 快速开始「约十几秒」vs 实测 6×300s 全灭；¥49 限时免费 vs 公告 ¥45 正式价 vs ¥68 含积分版）——逐页记口径+来源页，落档时钉死，别混用
4. **文档主张对照实测日志**：官方 FAQ 的处理建议（「创建卡住超 1 分钟就重新点创建」）与实际遭遇（每轮干等 300s）对照，是现成记分牌素材
5. **产出落到既有框架**：功能全景追加到该竞品既有档案/测试方案文件（新节「官方文档功能全景」，标注读取日期+来源页），每条功能映射对既有测试/对比框架的直接影响（新增考点、测试风险如「删除实例=记忆全丢」、积分约束），不是孤立存事实清单

### 全文合订本与判断回扫（2026-09-30 某AI通道服务 47 篇合订本实战）

用户发来官方文档离线合订本/全量 PDF（覆盖全部页面）时，价值不止于「归档+总结」——它是一次**对既有判断的全面审计**：

1. **原文归档先行**：复制到 documents/（去掉缓存文件名前缀，保留原名），再分段读（read_file offset/limit，每段 ≤2000 行，7263 行分 4 段读完再下结论）
2. **逐项对照既有判断（判断回扫）**：读完后把新文档的事实逐条对照当天/近期写入的所有下游工件——knowledge 档案、测试方案、todos 条目、待办提醒文案。部分来源（入口页+少数子页+旧公告）得出的结论被全文推翻是常态，某AI通道服务 实战同日翻车 3 处：「定时任务建设中」实已上线（智能/通知/脚本三类型）、「记忆黑盒看不见」实已可查看调容量、「绑支付=到期自动扣费」实为手动续费制（todos 里待办文案也一并修正）
3. **修正要版本化+向用户显著报告**：档案节升级 v2 并列出「v1 过时判断修正」清单（保留错误判断原文+修正依据），不静默改写；回复里把「重要修正」放在最前面——用户基于旧判断做的决策（如 10 月底防扣款操作）必须及时纠偏
4. **roadmap/「建设中」结论有保质期**：公告里承认没做完的能力是软肋金矿，但兑现速度以周计（7/15 公告的「建设中」三项，9/30 已上线两项半）。引用前必须核对最新文档确认现状仍然成立；拿旧 roadmap 当测试考点前先回扫——措辞从「它没有 X」降级为「它的 X 是裸配置 vs 我们的养成型」，否则对比框架的考点本身就是错的
5. **设计值 vs 实际使用是隐藏素材**：官方文档公开自家参数（如 MEMORY.md 设计 8-15 条）时，与己方实际运行数据对照（MyPS 条目 30+ 仍正常工作）=「养育超过设计」的活证据；原理篇把内部机制写成大众科普，本身也是赛道验证信号

### 深度分析层与吸收闭环（2026-09-30 二轮实战，用户两连纠）

**回扫修正只是底线，不是交付**。合订本读完、错误判断修正完，用户评「深度不够」——只做事实核对=校对员，不是分析师。修正完必须继续产出**结构分析**，检查单六个维度（某AI通道服务 实测全部命中）：
1. 文档本身的结构叙事：两类读者的篇幅分配（产品页给小白/原理篇给构建者）、重复出现的营销公式（收尾节×7/CTA×5）→ 漏斗判断
2. 产品 vs 引擎能力对照表：原理篇描述的能力逐项查产品页是否开放——白牌砍掉的功能清单暴露产品策略
3. 数据主权清点：导出/删除/注销/迁移四向核查（「四把锁」），对一个主打记忆的产品这是核心批判面
4. 计费与哲学的自洽性：产品定价模型是否养得活自家文档布道的理念（「卖 always-on、按预付电表收费」）
5. 白牌证据链：文档里的异常品牌名、URL 路径特征、上游官方站直链——推断必须标注证据强度
6. 关键词计数器：营销修辞、免责声明出现次数用正则钉死（「测试消息已发送只表示…」×7=他们自己最清楚哪里疼），引用带数字不带「很多次」

**批判与吸收必须成对出现**。深挖出「阉割版/四把锁」后用户立刻拉平衡：「肯定有很多独到的功能是可以借鉴的」——只有批判没有吸收地图=半个交付。产出**借鉴地图**四档格式：✅已对齐（对方只是把我们已有的做了面板）/🎯立刻抄/💤待议（有真实痛点再动）/❌不抄（写明理由）。所有候选项先过**用户能力边界过滤**（MyPS=skill/cron/prompt/memory 层，不碰代码——框架级功能不列进「可抄」）。

**吸收项当场落地，不等指令**。用户追问「是已经升级过了，还是只是讨论了在等我的指令？」——讨论层交付（「本周落地」）被认定为执行不力。纪律：借鉴地图里 skill/cron/prompt 层的改动**当轮直接实现并告知**（含新任务的档案落盘位置），只有需要拍板的架构级项才留待议；待议清单里不许出现低成本可立即执行的事项。借鉴项的讲解模板（用户认可）：它是什么 → 我们缺什么 → 抄完长什么样 → 值在哪，四段一条。

## 竞品实机对比测试模式（2026-10-01 某AI通道服务 实战）

纸面调研（文档精读/深度分析/借鉴地图）完成后的下一环：真机上手实测，产出「实操+对照」级素材（用户账号已验证的破圈形态）。用户当操作手（粘贴考题/回传截图），AI 当考官（出题/评分/入档/金句池）。要点：考题 A/B/C 三分类（公平项/不对等项/对方强项）、考点从竞品营销承诺与官方承认的限制反推、Reasoning 块泄露=判卷依据自交必截、送达以用户手机实际收到为准、评分用对方官方的「任务四要素」量它、新增环境感知题（先验时钟再测调度——某AI通道服务 时钟停在创建日慢 3 天实战）、埋题对考官零预存。完整协议（checklist/闸门设计/免费期收官）→ `references/competitor-live-testing.md`

## 延后深扒模式

用户说「先记上，回头再扒」「分析到这吧」时——柔性延后，不建待办/不设 Cron：

1. 在 knowledge 主题文件追加「后续安排」区块：状态 + 触发条件 + 深扒目标清单
2. 触发条件通常绑定 长期项目X 进展阶段（如「Execution 层/情绪模块设计进展到类似程度时」），不绑定日期
3. 连接点已挂到项目文件，触发时自然翻得到
4. 回复确认一句「已记，到时候说一声我直接扒」

## 输出要求

- 借鉴点必须映射到用户项目，不堆理论（用户是应用构建者不是研究员）
- 诚实标注项目局限（如「ESP32 玩具级，摄像头未启用」），别被亮点话术带偏
- 深扒提议给具体目标（哪个文件、哪部分），让用户一句话就能点头

## 已验证工具链

- GitHub 仓库页：web_extract 直接抓，README 摘要有效但长文会被截断——细节靠代码树 API 补
- 代码树：git/trees API 一次性拿全量文件（含 size），比逐目录 contents API 高效；web_extract 对 api.github.com 的 JSON 可能失败，用 curl 兜底
- raw.githubusercontent.com：抓单文件源码，无需 API token
- 2026-08-08 实战：竞品C 分析全流程走通，4 次 web_extract 完成「README + 全量代码树 + 关键目录 + 定位」

### ⚠️ 网络波动下的 GitHub 抓取降级路径（2026-08-10 实战）

抓取整仓库时按序尝试，别在一个方法上死磕：

1. `git clone --depth 1`（快则首选）→ 超时/卡死则放弃，别等
2. codeload tarball（`https://codeload.github.com/{owner}/{repo}/tar.gz/refs/heads/main`）→ 也可能超时
3. raw 直连逐文件 `curl`（单文件 2 秒成功过，但间歇性波动：同一文件几分钟后连超 60 秒）
4. **web_extract 抓 raw URL 最稳**——走服务端抓取，绕过本地到 GitHub 的波动链路；小文件返回全文，大文件（30KB+）给 LLM 摘要仍可用；一次最多 5 个 URL

经验：网络波动场景下别用后台脚本批量下载（后台进程全军覆没、每个文件空等 60 秒超时），改前台小批量（3-5 个）+ 短超时（25-30s）+ 失败的换 web_extract。下载到 /tmp 的内容要立刻复制到 knowledge/ 存档——/tmp 会丢。

## Pitfalls

- **部分来源结论会被全文推翻，引用前先回扫**：基于入口页+少数子页/旧公告下的判断，被全量文档翻车是常态（9/30 同日 3 处：定时任务/记忆管理/是否自动扣费）。拿到更全来源时，主动扫描当天写过的 todos、待办文案、knowledge 判断并修正——用户会基于这些判断做决策（如「到期前防自动扣款」），过期判断留在外面比留在档案里危害大
- **roadmap「建设中」清单是软肋金矿但易腐**：竞品兑现 roadmap 以周计，把它写进对比/测试框架时必须标日期，每次引用前核对最新文档是否仍成立
- **转述文章类调研（微博/公众号的项目清单），数字与状态必须实测**：GitHub API 逐个核 stars + README 实抓，文章数据滞后/定性过时是常态。实证（2026-09-29 十项目调研）：文章称 OpenMemory=「独立记忆基础设施」，实已转型为 coding session 移植工具（73 stars，旧版进 archive）；Hindsight 实际 40.9K（README 自标 26.8K 也滞后）；Letta 源码已并入 letta-code。不实测就会把过时信息当结论转述给用户
- 选型档案有「地层」：中间轮结论（补测/首测）与最终冻结/裁定并存时，引用前先查后者——用户会当场抓住过期结论（2026-09-22 Gemma/Qwen 实战，详见选型评估第 0 步）
- README 声称的功能（如「22 种情绪」）与代码结构可能不一致——以代码树核实为准
- **search_files 对中文 pattern 漏报（9/22 再度实测）**：在 knowledge/ 搜「主脑/Qwen/攻防」返回 0，terminal grep 同词命中 12 个文件。中文关键词检索 0 命中时必须 grep 复核后才能下「没有」结论
- 别在一个目录内容 API 上逐个爬（慢），trees?recursive=1 一次拿全
- 存档文件名用「项目名-分析」格式，便于和竞品文件（projectx-competitors.md）区分——参考项目 vs 直接竞品分开存
