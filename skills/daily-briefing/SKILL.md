# 早间简报

你正在执行早间简报任务。以下是完整的输出规则。

---

## 输出结构

按以下顺序生成简报。每个区块之间空一行。

### 1. 问候

一句自然的问候。不是「早安！新的一天开始了！」这种模板话。

**好的例子**：
- 「早上好。今天有三个定时待办到期，其中两个比较紧。」
- 「早。长待办那边，RAG 项目昨天完成了大纲，今天可以推进初稿了。」

**不好的例子**：
- ❌ 「亲爱的用户，早上好！又是充满活力的一天！」
- ❌ 「以下是您今日的日程安排：」

**风格**：搭档碰头语气。像早上碰面打个招呼，聊两句在忙什么。把扫描结果融入自然对话，不列清单。可以带一点对工作进展的观察或判断。

### 2. 长待办列表

遍历 data/todos.json 的 projects 数组，展示每个活跃项目（status: active 或 planned）。

**每个项目显示**：
- 项目名称
- 当前状态/进度
- 最近 2 个已完成子项及完成日期（来自项目 .md 文件的「已完成子项」区块）
- 如果没有已完成子项 → 不显示

**格式**：
```
🏔️ [项目名]
  状态：active
  最近进展：05-30 大纲定稿
```

### 3. 常规待办

完整列出 data/todos.json quick_tasks 数组中 done: false 的所有条目。

**日期分离规则**：扫描条目 text 字段，如有日期标记（如「（周六）」「明天」「下周一」等），自动分为两组：

1. **今日待办**：无日期标记或标记为今天的任务
2. **📅 待办（含日期）**：标记了未来日期的任务

如果某组为空则跳过。

**格式**：
```text
⚡ 常规待办（共 N 项）
  ├── 完成与合作方A的合同签订
  └── 等胶托到货 → 开发票 → 报销

📅 待办（含日期）
  ├── 用压条维修楼梯踏板（周六）
  └── 用捆扎带捆绑空调室外机连接管（周六）
```

如果超过 7 项，展示前 7 项 + 「还有 M 项」。如果为空，跳过此区块。

### 4. 必办待办

展示今天到期和即将到期的定时待办，以及持续生效的重要提醒。

**范围**：
- data/todos.json deadlines 数组中，截止时间在今天或未来 3 天内的、done: false 的条目
- **额外**：tags 含「重要」且 done: false 的条目**始终展示**（无论是否在 3 天内），直到用户解除

**格式**：
```
🔴 必办待办
  ├── 🔴 重要：市里实验室检查 6月8日起   [持续提醒]
  ├── ⏰ 今天 15:00  给张总发方案    [还剩 2h]
  ├── 📅 明天        提交季度报告    [还剩 1天]
  └── 📅 周三       项目评审会      [还剩 3天]
```

按截止时间排序，重要条目置顶。如果两项都没有，跳过此区块。

### 4.5. 每日必做

展示每日必须完成的生活习惯类事项，无条件展示。

**格式**：
```
🏋️ 每日必做
  └── 锻炼：[具体内容]（今天还没做）
```

**⚠️ 数据来源**：锻炼的具体内容（动作序列）应当在以下位置按优先级查找：
1. `USER.md` — 查看是否有「每日必做」或「锻炼」区块
2. `memory/preferences.md` — 查看是否有锻炼习惯描述
3. `memory/patterns.md` — 查看「健康规律」中是否有锻炼安排描述
4. 以上均无 → 使用通用描述「每日锻炼」（不复制技能示例中的动作序列作为用户数据）

以下示例仅为**格式演示**，不是用户数据，不要照搬：
```
🏋️ 每日必做
  └── 锻炼：腿部拉伸→肩部俯卧撑→收腹屈腿→俯卧撑→深蹲（今天还没做）
```

如果今日日记中已记录完成锻炼 → 显示「✅ 今日锻炼已完成」。

### 5. 善意提醒

检查之前标记的善意提醒候选，如果有则展示。

**来源**：
- Fragment Catcher 在碎片分类时标记的善意提醒信号
- 知识碎片中超过一周未解的「待消化」项
- 反复提及但未行动的事项（Cron 上下文可用 session_search 追溯）
- 长期未推进的活跃项目（创建超过两周、进度仍为 0%）
- 未确认完成的重要提醒（如取报告、办手续等——用 session_search 查最近提醒是否已被用户确认）
- **备份状态异常**：cron/backup-status.json 中 status 为 failed 或 success_via_api 时，在善意提醒中一笔带过（如「昨天的备份走了 API 通道，已成功推送」）

**格式**：温和语气，不强迫。

```
💡 顺便说一句
  你最近三次提到「整理客户资料」，但还没开始做。
  不急的话，可以找个碎片时间顺手处理了。
```

如果没有善意提醒候选 → 跳过此区块。

## 输出风格规则

1. **搭档碰头**：不是系统报告，是朋友间的早间沟通
2. **简短**：整个简报控制在 10 行以内。细节不展开
3. **结论先行**：先说最重要的事（定时待办），再说次要的
4. **不用感叹号**：用句号
5. **不用「我」开头汇报**：不写「我查看了你的待办列表」，直接给内容
6. **带温度**：可以根据待办数量和紧急程度加一句判断（「今天比较紧」「今天不算忙」）

## ⚠️ 事实性防错规则（2026-09-09 实战教训，违反即事故）

1. **日期只能引用原始记录，禁止自行换算**：行程/待办的日期一律照抄 todos.json text 里的原始表述（如「9/11 上午 某车次」），禁止把 deadline 换算成「明天/后天/下周」等相对词再输出——本次事故：deadline 9/11 被写成「明天去某市」（实际是后天），用户直接纠正。相对词只允许在确认无误时使用，拿不准就写绝对日期
2. **硬件/物流状态以最新事件档案为准**：涉及「在途/到货/已接入」类状态，必须先查 data/events/ 与 data/diary/ 的最近记录确认当前状态，禁止凭会话印象或旧消息写状态——本次事故：USB 麦克风 9/8 已到货接入验证（events 11:58 有记录），简报仍写「在途」
3. **写完自查一遍所有日期和状态**：推送前把简报里每个日期与 todos.json/events 原始记录对照一次，日期不一致 = 返工

## 数据来源

| 区块 | 数据来源 |
|------|---------|
| 问候 | 当前日期 + 整体待办概况 |
| 长待办 | data/todos.json projects + data/projects/*.md |
| 常规待办 | data/todos.json quick_tasks |
| 必办待办 | data/todos.json deadlines |
| 备份状态 | cron/backup-status.json — 如 status 为 failed 或 success_via_api，在问候或善意提醒区块中一笔带过 |

### ⚠️ 部署前置条件（Cron 运行时）

本技能使用相对路径读取数据（`data/todos.json`、`data/projects/*.md`），这些路径相对于 `~/.hermes/` 解析。

触发本技能的 Cron 任务**必须**设置 `workdir='~/.hermes'`，否则：
- `data/todos.json` 解析为 `~/data/todos.json` → 文件不存在（workdir 未设时解析为 `~/.hermes/data/todos.json` 也需确认文件是否存在）
- `data/projects/` 解析为 `~/data/projects/` → 目录不存在
- 所有数据源返回空 → 输出 `[SILENT]` → 微信端静默不推送

**路径确认**：`todos.json` 位于 `data/todos.json`（非 `~/.hermes/todos.json`）。首次执行时先用 `read_file` 或 `search_files` 确认路径再读取。

**数据采集实测坑（2026-09-09 Cron 实跑沉淀）**：

1. **search_files 静默返回 0 ≠ 数据为空**：本次实跑中 `search_files` 对确实存在的路径（`data/projects/*.md`、USER.md 内容检索）全部返回 `total_count: 0`。返回 0 时先怀疑工具，再怀疑数据——用 terminal `ls <dir>` / `grep -n` 兜底确认，确认存在后改用 `read_file` 直接读。误判为空数据是错误 `[SILENT]` 的直接来源。
2. **todos.json 分页陷阱**：文件已超 790 行，`read_file` 单次只给前 500 行。未完成的 deadlines 全在 `offset=501` 之后（dl-026 某市行程、dl-039 灭火器、dl-041 当天到期项都在后半段）——漏读后半段会漏掉最关键的必办待办。读一次不够就续读，读完再汇总。
3. **未注册项目文件**：`data/projects/` 下可能有未登记进 todos.json projects 数组的活跃项目（实例：eidos-projectx.md）。遍历 todos.json 之余 `ls data/projects/` 交叉核对，发现 status: active 且有近期进展的孤儿项目，在长待办区块补一行。
4. **同状态项目合并展示**：多个长待办若最近子项完全相同（如三个资料整理项目共用同一条「9/8 状态确认：检查通过，有空补充即可」），合并成一行展示比逐项列三行更符合「搭档碰头、简短」的语气要求。

**验证方法**：Cron 执行后检查 `last_status=ok` 不代表用户收到了内容。必须确认 Cron 的 workdir 已设置且数据文件可读。手动运行一次 `cronjob(action='run', job_id='<id>')` 验证输出内容。
