# 提醒引擎

你正在执行提醒管理任务。以下是完整的处理规则。

---

## 自动提醒判断逻辑

```
Fragment Catcher 捕获到待办
  │
  ▼
有明确截止时间？
  │
  ├── YES → 创建提醒
  │   ├── 读取 USER.md 提醒偏好
  │   ├── 计算提醒时间点
  │   ├── 创建 Cron 任务
  │   └── 将 Cron ID 写入 todos.json 的 reminder_cron_id 字段
  │
  └── NO → 不创建提醒
      ├── 琐碎事务 → 放入常规待办
      └── 长期事项 → 放入长待办
```

---

### 持续提示型提醒（直到用户解除）

**适用场景**：用户要求持续提醒某一事项，直到主动说「解除」「停止」「不用再提醒了」。

**规则**：
- 创建每日 Cron（`0 9 * * *`），repeat 设为 forever
- 提示内容随时间变化（事件前显示倒计时，事件后切换为执行中提醒）
- 在 Cron 的 prompt 中写入日期判断逻辑（如「如果今天在 X 月 X 日之前…否则…」）
- 用户说「解除」时，定位该 Cron ID → 执行 cronjob action='remove'
- 同时在 todos.json 中将对应条目标记 done: true

**与硬期限提醒的区别**：
- 硬期限提醒：到期即停或转过期升级
- 持续提示型：没有自然到期日，靠用户主动喊停

## 提醒类型

支持三种提醒模式：

### 模式一：硬期限提醒（定时待办）

用于有明确截止时间的一次性任务，如「周三前交报告」。

### 模式二：持续提醒（直到用户叫停）

用于需要每日提醒、直到用户明确说「解除」的场景，如「市里来检查」「重要倒计时」。

**创建规则**：
- 设 Cron 为每日（`0 9 * * *`），repeat=forever
- 提醒内容需根据当前日期动态计算（距目标日还有 X 天 / 目标日已到）
- 告知用户：「要解除提醒时跟我说一声就行」

**清理规则**：
- 用户说「解除」→ 用 cronjob(action='list') 查出对应 job_id → cronjob(action='remove', job_id=...)
- 同时将 todos.json 中对应 deadline 条目标记 done: true

### 模式三：过期升级提醒

适用于硬期限任务过期后的持续追问。

### 模式四：验证型一次性提醒（外部系统行为求证，2026-10-01 实战）

MyPS 当「考官/验证者」时，需要确认**外部系统**（竞品 bot、第三方服务、他人所设提醒）在它声称的时间点是否真的执行。做法：设一次性 cron，在宣称触发时刻后 ~10 分钟向用户问一句。

规则：
1. **prompt 自包含三要素**：问什么（一句话）；结果二分映射（弹了→判 A 什么、没弹→判 B 什么）；结果写到哪个 knowledge 文件的哪个条目（读文件定位后追加，标注「MM/DD HH:MM 验证」字样）
2. **求证不是催办**——prompt 显式写「这是测试求证，不是催办」，防止用户误以为是任务提醒
3. 时点贴着被验证事件（对方宣称 16:31 触发 → 16:40 问）；多个验证点遵守同 RPM 错峰规则
4. 结果落档后该 cron 使命即终（一次性），无需清理；用户答复后当场更新测试日志

实战：某AI通道服务/ClawBot 对比测试——「消防自查表提醒-周四」实证 10/1 09:31 已弹（归档）；「血压提醒」自称 10/2 16:31 首发 → 设 16:40 问询 cron 终审「编造 vs 能力有但日期算错」。

## 提醒时间计算

### 硬期限提醒（定时待办）

读取 USER.md 中的提醒偏好，默认策略：

| 提醒节点 | 时间 | 内容 |
|---------|------|------|
| 首次提醒 | 截止前 24 小时 | 「[任务名] 明天到期，当前状态未完成」 |
| 再次提醒 | 截止前 2 小时 | 「[任务名] 2 小时后截止」 |
| 升级提醒 | 过期后每 4 小时 | 「[任务名] 已过期 [X] 小时，是否已完成？」 |

### 长周期策略（截止时间 > 30 天）

适用于填报、申报、年度检查等跨度长、有固定截止时间的任务。

当从当前日期到截止日期 > 30 天时，在默认 24h 策略之上增加中期提醒：

| 提醒节点 | 时间 | 内容 |
|---------|------|------|
| 中期提醒 | 截止前 7 天 | 「[任务名] 还有一周截止（[截止日期]）」 |
| 首次提醒 | 截止前 24 小时 | 「[任务名] 明天到期，当前状态未完成」 |
| 再次提醒 | 截止前 2 小时 | 「[任务名] 2 小时后截止」 |
| 升级提醒 | 过期后每 4 小时 | 「[任务名] 已过期 [X] 小时，是否已完成？」 |

**创建方式**：中期提醒和截止日提醒各创建一个一次性 Cron，名称分别标注「（提前一周）」和「（截止日）」。将截止日 Cron ID 写入 reminder_cron_id 字段。

### 用户指定提前期（覆盖默认策略）

当用户明确说「到期前 X 天提醒」「提前 X 日开始提醒」时，**优先使用用户指定的提前天数**，不套用默认策略。

**处理规则**：
- 用户指定提前期 → 以用户指定为准，忽略 24h/2h/7d 默认策略
- 单一提醒 vs 持续提醒：用户说「提前3天提醒」通常指从那天开始持续提醒（每日），而非一次性的。除非用户明确说「提前3天提醒一次」
- 创建方式：设一个每日 Cron（`0 9 * * *`），prompt 中写入日期判断逻辑——今天 >= 开始提醒日 时才输出提醒内容，之前的日子静默
- 截止日过后，提示内容自动切换为「已过期，请尽快处理」

**示例**：SSL 证书 9月7日到期，用户说「到期前3日开始提醒」
→ 开始提醒日 = 9月4日
→ Cron 每日 9:00 运行，prompt 判断：< Sep 4 静默，>= Sep 4 且 <= Sep 7 推送到期提醒，> Sep 7 推送过期提醒

### 静默期处理

如果在静默期（23:00 - 08:00）触发了提醒：

- 不立即推送
- 在次日 08:00 集中推送所有静默期积累的提醒
- 如果是硬期限在静默期内到期 → 仍在到期时间推送（不受静默期限制）

## 会面/约见类提醒（不同于交付任务）

用户有明确会面安排（「周一上午和X见面」「约了X谈事」）时，**不套用 24h+2h 硬期限策略**——那是交付任务导向的，对会面来说 2h 前提醒往往已过时（上午的会，10 点提醒就晚了）：

| 项 | 做法 |
|---|---|
| deadline | 按"上午/下午"设占位截止（上午→当天 12:00，下午→当天 18:00），用于简报展示 |
| 提醒 | **当天早晨出门前一次性提醒**（用户作息 ~5:50 起、8:30 上班，会面日设 07:30 左右），prompt 含会面对象+事由+「出门前确认时间地点」 |
| 交付 | 用户作息已知时贴近出门时间；不确定时优先早晨 7:30 |
| 记录 | diary + events 双重写入（约见安排既是主观安排也是客观事件），todos.json 加 deadlines 条目 tags 含「会面」 |

> 实战：2026-08-28「周一上午和卫健委徐老师见面（聊检验所出让部分面积）」→ dl-031（deadline 8/31 12:00）+ 一次性 Cron 8/31 07:30。

## 出行/出发类提醒（跨天行程，不同于会面）

用户给出明确出行安排（「X号去某市」「X号坐 某车次/某车次」）时，**先确认出发的具体时刻（上午/下午/晚上），再定提醒时间**——只按"出发日期"设提醒会踩坑：

| 出发时刻 | 提醒时间 | 理由 |
|---|---|---|
| **上午出发**（车次/航班在中午前） | **出发前一日 20:00 左右** | 当天上午就走，出发日任何时段的提醒都可能已晚（实战：9/11 上午 某车次，若设 9/11 晚 20:00 人已在某市） |
| 下午/晚间出发 | 出发当日 12:00 前后 | 上午还有准备窗口 |
| 不确定时刻 | 出发前一日 20:00（保守） | 提前总比晚好，提醒内容让用户核对 |

**提醒内容组装**：出行提醒应含完整行程核对清单（车票/证件、报到或办事材料、住宿订单、返程票），细节从 todos.json deadline 条目的 text 字段（需存完整行程）或 knowledge 家庭/行程档案提取。

**同步动作**：行程细节（车次/酒店/返程/时间点）更新进 todos.json text + knowledge 相关档案，不只放提醒 prompt——简报与改期都要用。

> 实战：2026-09-03 某市送站 dl-026——行程 9/11 上午 某车次 出发、9/13 晚 某车次 返程 21:00 到家。初次设提醒 9/11 20:00 是错的（当天上午已出发），修正为 9/10 20:00 出发前一晚核对（车票证件/录取通知书/民宿订单/某车次 返程票）。行程全细节已写入 dl-026 text + knowledge/家庭-孩子研究生.md。

## Cron 任务创建

### 重要：平台适配前置检查

在创建任何 Cron 任务之前，先确认当前用户的连接平台：

**微信平台特殊要求**：
- `deliver: origin` 在微信平台下可能无法正确路由到用户会话
- 必须使用显式微信 chat ID 格式：`deliver: 'weixin:<chat_id>'`
- chat_id 可通过 `send_message action='list'` 获取，或从当前会话信息中提取
- **同时必须设置 workdir**：如果 Cron prompt 中会读取相对路径的数据文件（如 `data/` 下的内容），需要设置 `workdir='~/.hermes'`，否则技能中的相对路径会解析到错误位置

**其他平台**：`deliver: origin` 通常工作正常，但 workdir 规则同样适用。

> 经验教训：不设 workdir 的 Cron 从用户 HOME 目录启动，`data/diary/` 解析为 `~/data/diary/` 而非 `~/.hermes/data/diary/`，导致数据读取为空，输出被静默抑制（[SILENT]），用户端完全收不到推送。即使 `last_status=ok`，也不代表消息已到达用户。

### 创建流程

1. 从 Fragment Catcher 接收待办信息（任务内容、截止时间、关联项目）
2. 读取 USER.md 确认提醒偏好
3. 计算提醒时间点
4. 检查用户连接平台，确定 deliver 目标格式
5. 如果 Cron prompt 中使用了 `data/` 等相对路径 → 设置 workdir
6. 创建 Cron 任务，设置：
   - 名称：`reminder-[任务简称]`
   - 触发时间：根据计算结果
   - 提示内容：包含任务名、截止时间、当前状态
   - 推送方式：平台适配后的 deliver 目标
   - workdir：如需要则设置
7. 将 Cron ID 记录到 todos.json 的 `reminder_cron_id` 字段
8. **创建后逐字符核对 deliver 地址**（2026-09-09 实战：微信 chat_id 抄错一个字母 k→n，任务会静默投递到不存在的会话，用户永远收不到且 last_status 不报错）——从 cronjob 返回的 JSON 里复读 deliver 字段确认与当前会话 chat_id 一致
9. 返回确认信息

### ⚠️ 同一时段多 Cron 的 RPM 间距（2026-09-09 实战）
同一 key 后端（GLM 等）有**每分钟请求数（RPM）独立限制**，与总量配额无关——多个 cron 挤在同一分钟触发（如简报 8:33 + 收尾 8:35）加主会话并发，三路 agent 同时打 API 会集体 429（"Rate limited after 3 retries"）。创建规则：
1. 同一时段的多个 cron **至少错开 10 分钟**
2. 与主会话高密度工作重叠的时段，避免再排新 cron
3. 429 是频率限流不是额度烧尽——窗口滑动自动恢复，处理方式是错峰重跑，不是加配额

### Cron 任务格式

一次性提醒（具体时间点）：
```
名称：deadline-[任务简称]
触发：YYYY-MM-DDTHH:MM:00
提示：「提醒：[任务名] [X] 小时后截止，当前状态未完成。」
推送：weixin:具体chat_id  （微信平台）或 origin（其他平台）
workdir：~/.hermes  （使用了相对路径时必设）
```

### 微信平台 chat_id 陷阱
- **deliver 的 chat_id 必须从既有配置/记忆复制，禁止凭记忆手打**——2026-09-09 实战：`<你的微信ChatID>Pukw` 手打成 `<你的微信ChatID>Punw`（k→n 一字之差），创建后才发现，靠 remove+重建修正。chat_id 从 cron list 已有任务、历史会话或 send_message action='list' 复制原文

### ⚠️ 一次性 Cron 的 schedule 参数格式陷阱

创建一次性 Cron 时（2026-08-01 实战踩坑三次）：

- **正确**：`schedule='2026-08-10T20:00:00'`（ISO 时间戳），且**不要**同时传 `repeat` 参数（缺省即 once）
- **错误**：`schedule='once at 2026-08-10 20:00'` → 报「Invalid schedule」
- **错误**：ISO 时间戳 + `repeat='once'` 同时传 → 报 TypeError `'<=' not supported between instances of 'str' and 'int'`
- 创建成功后 job 的 schedule 字段显示为 `once at 2026-08-10 20:00`，那是系统内部渲染格式，**不是**入参格式——别照着返回值写回去
- 长周期任务的「提前一周」「截止日」提醒同理：各建一个 ISO 时间戳的 once 任务

过期升级提醒（周期性）：
```
名称：overdue-[任务简称]
触发：0 */4 * * *  （每 4 小时）
持续：直到任务标记完成
提示：「[任务名] 已过期，是否已完成？」
推送：weixin:具体chat_id  （微信平台）或 origin（其他平台）
workdir：~/.hermes  （使用了相对路径时必设）
```

### ⚠️ Cron 并发密度与 LLM 限流（2026-09-09 实战）

同一 provider key 同时服务：主会话 + 多个 cron agent。密集排布的 cron（如简报 08:33 + 收尾 08:35）与主会话报告生成叠加时，短时并发触发 provider RPM 限流（HTTP 429「您的账户已达到速率限制」），agent 重试 3 次失败、任务静默失败（GLM Coding Plan 5 小时额度才用 2% 也照样限——限的是每分钟请求数，不是总量配额）。

规则：
1. 同一时段多个会调 LLM 的 cron **至少错开 10 分钟**；创建前先 cronjob list 看邻近任务，避开时间簇
2. 429 自愈（限流窗口滑动即恢复），不用换 key——错峰重跑即可；报告类收尾任务失败重跑无数据损失
3. 长测试的收尾 cron 与 daily-briefing（08:30）这类固定任务同日时，排在 08:45 以后

## 待办改期重调度

### 触发条件

用户将已有定时待办改到新日期（「X 改到明天」「只复查的事，明天去」），Fragment Catcher 识别后调用本引擎执行。

### 处理流程

1. 从 todos.json 读取该待办的 `reminder_cron_id`
2. 用 cronjob(action='list') 确认旧 Cron 是否仍存在
   - 旧 Cron 存在 → cronjob(action='update', job_id=..., schedule=新时间)，同步更新 prompt 中的日期文案
   - 旧 Cron 已不存在（曾被清理/丢失）→ 按「创建流程」新建一次性 Cron，把新 ID 写回 `reminder_cron_id`
3. 更新 todos.json：deadline 改为新日期，text 注明新安排（如「——8/1（周六）去」）
4. 记录改期事件到 data/events/ 当日文件
5. 回复确认新日期与提醒时间

> 经验：改期时旧 Cron 可能早已被清理（列表里查不到），不要假设它还在——先 list 确认，缺失则直接新建。

## Cron 任务清理

### 触发条件

- 用户说某个待办已完成
- Fragment Catcher 识别到待办完结信号
- 手动标记待办为 done

### 清理流程

1. 从 todos.json 读取该待办的 `reminder_cron_id`
2. 删除对应的 Cron 任务
3. 将 `reminder_cron_id` 设为 null
4. 如果有过期升级提醒的 Cron → 一并删除

## 提醒偏好读取

每次创建提醒前，读取 USER.md 的「提醒偏好」区块：

| 偏好项 | 默认值 | 说明 |
|--------|--------|------|
| 可打扰时间 | 08:00 - 23:00 | 此时间段内可主动推送 |
| 静默期 | 23:00 - 08:00 | 非紧急提醒延迟到 08:00 |
| 硬期限策略 | 24h + 2h 双重 | 过期后每 4h 升级 |
| 每日简报 | 08:30 | 由 daily-briefing Skill 处理 |
| 每日晚间 | 22:00 | 由 daily-review Skill 处理 |

如果用户修改了 USER.md 中的提醒偏好，新创建的 Cron 任务使用新偏好。已创建的 Cron 任务不受影响。

## 提醒执行（Cron 触发时的消息组装）

一次性提醒 Cron 触发时，prompt 通常只是一句静态提醒。**不要直接复读 prompt**，先组装上下文再推：

1. **定位待办条目**：读 todos.json（用**绝对路径** `~/.hermes/data/todos.json`——提醒 job 常未设 workdir，相对路径会解析失败返回空），按 `reminder_cron_id` 或文本匹配找到对应 deadline 条目
2. **提炼状态历史**：deadline 条目的 `text` 字段会随时间积累运行日志（如「8/25 被拒（财务数据问题）」「整改一直没动」）——把关键状态提炼进提醒，用户才知道**为什么**急
3. **追溯最近进展**：session_search 查用户最近是否提过该事项（完成/整改/推迟），避免提醒已过时的事项
4. **查同日冲突**：扫 todos.json 中同日其他 deadlines/会面（如截止日当天中午有会面），提醒里顺带一句时间安排建议
5. **风格**：SOUL.md 语气——结论先行、去掉 prompt 里的感叹号、不堆 emoji

> 实战：2026-08-31 科技型填报截止日提醒——prompt 只有一句话，但 todos.json 显示 8/25 被经开区驳回（财务数据）、整改一直未动、当天中午还有卫健委会面（dl-031），组装后提醒才真正可执行。
