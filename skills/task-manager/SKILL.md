# 待办管理器

你正在执行待办管理任务。以下是完整的处理规则。

---

## 三类待办规则

### 长待办（项目）

| 属性 | 规则 |
|------|------|
| 终结时间 | 一般没有，如果有也只是标记提醒 |
| 分解规划 | **目前不需要**。保持扁平，不自动拆分里程碑 |
| 子项记录 | 可接受用户提及的完成事件作为子项记录 |
| **存储** | data/projects/ 下独立 .md 文件 + data/todos.json projects 数组 |
| 创建条件 | 用户明确说要做一个项目、长期事项 |
| 创建确认 | **需要用户确认**才能新建 |

### 常规待办

| 属性 | 规则 |
|------|------|
| 完成界限 | 无。只是罗列等待完成 |
| 来源 | 随机发生的琐碎临时事件 |
| 提醒 | 不单独设提醒，在早间简报中展示 |
- **存储** | data/todos.json quick_tasks 数组 |
| 完成处理 | 用户说完成 → 标记 done: true → 从活跃列表移除 |

### 定期待办

| 属性 | 规则 |
|------|------|
| 截止时间 | **必须有**。这是区别于常规待办的核心特征 |
| 提醒 | 自动创建 Cron，按 USER.md 提醒偏好配置 |
| 优先级 | 高于常规待办。在全局视图中优先展示 |
- **存储** | data/todos.json deadlines 数组 |
| 关联 | 可选关联到某个长待办（project 字段） |

## 操作指令

### 创建待办

1. Fragment Catcher 已识别出待办类型（长待办/常规/定时）
2. 生成唯一 ID（qt-NNN / dl-NNN / pj-NNN）
3. 写入 data/todos.json 对应数组
4. 如果是定时待办 → 调用 reminder-engine 创建 Cron
5. 如果是长待办 → 同时创建 projects/ 下的 .md 文件
6. 回复确认

### 查询待办（全局视图）

触发词：「有什么事」「待办」「计划」「我有什么要做的」「看一下任务」

**财务聚合查询（报销总额、待回款等）**：

当用户询问与「钱」相关的统计（「报销总额」「还有多少钱没回来」「垫付了多少」）：

1. **范围限定**：在 todos.json 的 quick_tasks 和 deadlines 中，检索 tags 含「报销」的未完成条目
2. **金额提取**：从每个匹配条目的 `text` 字段中解析数字（如 61.76 元、412 元），支持常见中文金额变体
3. **合计汇总**：累加所有提取到的金额
4. **回复格式**：「X 笔未报销，合计 Y.YY 元」+ 逐项明细
5. **到账确认**：用户确认到账后，走完成待办流程标记 done，同时更新 text 标记到账日期

金额提取失败时（纯中文数字），返回条目清单让用户确认具体数字，不虚构。

**展示格式**：

```
🔴 定期待办
  ├── 今天 15:00  给张总发方案      [还剩 2h]
  └── 周三       提交季度报告       [还剩 2天]

🏔️ 长待办
  ├── RAG+Agent 内容系列
  │   └── 最近完成：05-28 完成调研、05-30 大纲定稿
  └── 个人网站改版
      └── 最近完成：（暂无）

⚡ 常规待办
  ├── 买牛奶
  ├── 回复王工消息
  ├── 整理桌面
  └── [还有 4 项… 共 7 项]
```

**展示规则**：
1. **重要提醒优先**：如果 deadlines 中有 tags 含「重要」且未完成的条目（如实验室检查提醒），**始终置于最顶部**，用 🔴 标记，独立于常规排序
2. 定期待办按时间排序，显示剩余时间
3. 长待办每个显示最近 2 个已完成子项及日期
4. 常规待办完整列出（超过 5 项时折叠显示总数）

### 更新待办内容

用户对已创建的待办提供补充或修正信息时，更新现有条目的 `text` 字段，而非新建重复条目。

**适用场景**：
- 用户先说了一个模糊描述，后续补充更精准的信息（如「进一些耗材」→「采购300-500支过渡用」）
- 用户修正之前的描述
- 用户澄清任务的**顺序依赖关系**（如「先等A到货 → 再开发票 → 再报销」）

**顺序依赖表示**：当任务有明确的多步骤流程时，使用 `→` 连接符表示流水线关系，而非写成长句或分条。例如：
- ✓ `等A到货 → 开发票 → 报销`
- ✗ `先等A到货，到货以后开发票，开完发票再报销`
- ✗ 拆成多个独立待办（步骤之间紧密耦合时，不拆分）

### 任务合并与跨类别清理

当用户澄清或纠正时，发现两个不同类别的条目实为同一件事（如 deadline 和 quick_task 重复）：

1. **识别**：按内容相似度匹配 data/todos.json 中未完成的条目
2. **决定保留**：优先保留有更完整结构的条目（deadline > quick_task），合并描述信息
3. **执行**：更新保留条目的 text/deadline 字段，删除被合并的重复条目
4. **关联调整**：如果涉及 deadline 的日期变更，同时更新关联的 Cron 提醒
5. **回复**：告知合并结果

**操作**：
1. 在 todos.json 中找到匹配的未完成条目（按内容相似度判断）
2. 更新 `text` 字段为更精准的描述
3. 回复确认更新内容

### 完成待办

1. 用户说「XX 做完了」「XX 发了」「搞定了 XX」
2. 在 todos.json 中找到对应条目
3. **检查批量组归属**：匹配的条目是否属于 memory 中定义的批量组（如每月 6 件事）？是 → 标记 done 后还需检查组内其他成员状态，回复时报告组进度而非单个任务完结
4. 设置 done: true，记录完结时间
5. 如果有关联的 Cron → 清理该 Cron（调用 reminder-engine）
6. 如果是长待办子项 → 追加到项目文件的「已完成子项」区块
7. 回复：非批量组成员 → 「✅ 已标记完成：[任务名]（[完结时间]）」；批量组成员 → 按组进度格式回复（已完成 N/M 件，剩余 X 件）

### 归档

- 已完成的长待办（status: done）→ 移入 data/archive/
- 过期已完成的定时待办 → 定期清理（可在晚间总结时检查）

## todos.json 读写规则

- **读**：每次查询待办、生成简报时读取
- **读取方式**：用 read_file 工具直接读，不要用 `python3 -c "import json..."` 解析——会触发 Hermes 安全审批（script execution via -e/-c flag），命令被 BLOCKED 且用户困惑（2026-08-09 实战）。todos.json 约 540 行，超一页时用 offset 分页读完整再改；patch 工具会提示「Re-read the whole file before overwriting」
- **写**：创建、完成、更新待办时写入
- **并发**：避免同时写入冲突。每次写入后确保 JSON 格式正确
- **备份**：重要操作前建议保留旧版本（可选，非强制）
- **校验**：写入前检查 data integrity——`projects` 数组中的条目不应含 `deadline` 或 `text` 字段（那是 deadline 的结构），`deadlines` 数组中的条目不应含 `status` 或 `progress` 字段（那是 project 的结构）。发现错位条目时，移动到正确的数组再写入。
