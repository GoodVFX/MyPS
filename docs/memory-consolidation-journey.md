# 记忆系统 consolidation 与 journey 成长回放机制

MyPS v4.0 的两块记忆基础设施升级：**每日水位自主整理**（daily-review 步骤 7.5/7.6）与**每月成长回放**（journey cron）。两者共享同一数据源（waterlevel.log），构成「日维护 → 月回放」的记忆生命周期闭环。

设计借鉴：Letta（原 MemGPT）的 dreaming、Hindsight 的 reflect 闭环，以及记忆占用百分比趋势观测的原理篇写入标准。

---

## 1. 背景

MyPS 的记忆分两层：

| 层 | 位置 | 特点 |
|----|------|------|
| 注入层 | `~/.hermes/memories/MEMORY.md` | § 分隔条目，约 2200 字符上限，**每个会话都全文注入**，是记忆系统的「内存条」 |
| 知识层 | `~/.hermes/data/knowledge/` | 按主题一个文件，容量无上限，靠索引检索 |

注入层的核心矛盾：**容量固定，事实持续产生**。写满后 memory 工具直接报错（`Replacement would put memory at X/2200 chars`），新记忆存不进去，且用户不会主动发现。

v3.0 时代的行为是「发现满了 → 提醒用户清理」——依赖用户抽空手动处理，实践中长期挂起。v4.0 升级为 **cron 自主整理**：水位到阈值，当晚自动执行，用户只看结果。

---

## 2. 方案

### 2.1 每日水位记录（步骤 7.5 前置，无条件执行）

每晚 daily-review 运行时，先向 `~/.hermes/data/journey/waterlevel.log` 追加一行：

```
YYYY-MM-DD|字符数|条目数
```

- 字符数用 `len(open(...).read())` 统计（**不要用 `wc -c`**——它返回 UTF-8 字节数，中文每字约 3 字节，会把 1630 字符误报成 4894「字节」，虚高一倍）
- 条目数 = § 分隔的条目行数
- 并在总结中报一行：`🧭 记忆水位 N/2200（P%），较昨日 ±M`；log 无前日记录（首晚）只报当前值
- **同日多行合法**：白天会话写入方与晚间 daily-review 各记一行是正常现象，两行都是事实，按行序看演化，不要去重

趋势本身是决策信号：快涨 = 记太杂该挤水；平稳 = 健康。

### 2.2 水位触发的自主整理（步骤 7.5）

- **水位 < 1900（86%）** → 记录趋势后跳过，不做整理
- **水位 ≥ 1900** → 执行一轮整理，流程：

1. **快照先行**（回滚锚点）：`cp memories/MEMORY.md memories/MEMORY.md.pre-consolidation`（覆盖旧快照即可）
2. 合并同主题条目（运维类、工具链类多条合一）
3. 删除已过期事实（已完结的截止、被翻案的中间结论、已变化的瞬时状态）
4. 压缩表述（去冗余括注；与 USER.md 重复的画像细节改指针）
5. 写入后复测水位，输出一行结果（如 `🧹 记忆整理：28→26 条，2180→1966`）

**整理判据**（决定一条目去留）：

- **三个月判据**：该条目三个月后是否仍然成立？不成立的删除，或降级到 knowledge/ 留痕
- **状态类条目必须带时间锚**（如「服药 7/12 起」）——无锚的过期事实冒充「当前状态」风险最高
- **硬约束——事实无损**：决策类条目（拍板/冻结/规则/教训）只压措辞不删内容；拿不准是否过期的保留
- **评估后无可整也是合法产出**：判据全过、无合并组、措辞已密时，报一行评估结论即可（如 `🧹 记忆体检：29 条全过判据，无可整，水位 2099`），不做名义性压缩——该状态说明水位上涨来自高价值新增而非垃圾堆积

**实战打法**（两轮实测沉淀）：

- **整档重写优于逐条 patch**：条目多时（27+ 条）在脚本里重建 entries 列表整体写回，比逐条 patch 快且不误伤；快照先行即是回滚锚点
- **三轮压缩的收益结构**：第 1 轮逐条措辞压缩约省 10%；第 2 轮砍前缀与重复修饰再省小几成；真正达标靠第 3 轮——①与 USER.md 比对去重（重复画像细节改指针）②已完结事件的 knowledge 指针退役给索引层
- **事实无损验证——must_have 清单法**：重写前列一份关键词清单（每个事实一个标记），写回后逐个验证存在性，缺失项逐个确认是「有意退役」还是「误删」
- **收益预期管理**：纯措辞压缩每轮上限约 10-15%；水位严重超限（>2400）时必须靠合并条目 + 删过期事实
- **合并优先找簇**：同一主题被多条从不同日期写入的条目簇，是主要压缩收益来源，不是找废话

### 2.3 记忆固化提案（步骤 7.6，reflect 闭环）

每晚总结完成后，回顾当日全部内容自问：「今天有什么是值得**新会话的我**长期记住的？」

- 有 → 总结末尾追加提案区块（候选最多 3 条，宁缺毋滥），用户回复「固化」或指出编号后当晚写入
- **准入唯一标准是三个月判据**；黑名单五类不提案：一次性情绪、临时任务参数、模糊态度、对话可实时推断的信息、未经用户确认的敏感信息
- 用户未回复 → 不写入；候选顺延观察，连续 2 晚未确认则放弃
- 无候选 → 跳过区块，不输出空模板

### 2.4 月度成长回放（journey cron）

每月 1 日早间 cron 统计上月成长轨迹，产出双份：

1. **档案**：`data/journey/YYYY-MM.md`（已存在则覆盖），五段结构：技能沉淀 / 记忆演化 / 里程碑 / 待办完成 / 本月叙事
2. **推送**：≤400 字摘要发用户

数据源四类（不读会话原文）：

- git log/stat：skills/ 新增、MEMORY.md 变更、knowledge/documents 新增
- diary 当月关键节点（≤6 条）
- todos.json（⚠️ 无完成时间戳，口径必须是「当月创建且已完成」）
- MEMORY.md 水位 + `data/journey/waterlevel.log` 趋势

**waterlevel.log 是本机制的数据前提**——7.5 每晚记录的水位行，就是月度回放「记忆演化」段的原始数据。勿删改日志格式。

## 3. 部署

前置：v4.0 基础系统（daily-review cron 已运行）。

1. daily-review 的 SKILL.md 已含步骤 7.5/7.6——确认 cron 任务加载的是 v4.0 版 skill
2. 创建 journey cron（示例）：

```
cronjob action='create'
  name='MyPS成长回放'
  schedule='47 8 1 * *'          # 每月 1 日 08:47（错峰，避开整点任务）
  skills=['daily-review']        # 或独立 skill
  prompt=（任务四要素：统计上月 → 写档案 data/journey/YYYY-MM.md → 推送 ≤400 字五段摘要）
  deliver='weixin:<你的微信ChatID>'
  workdir='~/.hermes'            # ★ 必设，否则相对路径读不到数据
```

3. 新 cron 机制上线即模拟测试（不要等真实触发日）：
   - ⚠️ 相对时间 prompt 会测错分支——先 `update` 把范围 pin 死到具体月份跑模拟，跑完改回通用版
   - 模拟跑的档案产物会被正式首跑同路径覆盖，无残留风险
4. 验证链：模拟测试 → 首个自然触发日挂一次性 CHECK cron（机械判据：last_status / 产物 mtime / 与 git 原始数据交叉抽查）→ 全绿后才进入发布流程

---

## 4. 验证

部署后按此清单机械验证（禁止「看起来正常」）：

| 判据 | 方法 |
|------|------|
| 水位行在写 | `waterlevel.log` 最新行日期 = 今天，格式 `YYYY-MM-DD\|字符数\|条目数` |
| 字符数准确 | log 中的字符数 vs `len(open('memories/MEMORY.md').read())`，±5 容差 |
| 整理触发正确 | 水位 ≥1900 的当晚，输出含 🧹 整理行；<1900 的当晚无整理动作 |
| 快照存在 | 整理发生过时 `memories/MEMORY.md.pre-consolidation` 存在 |
| 事实无损 | must_have 关键词清单逐项 `in` 验证 |
| journey 档案 | 每月 2 日检查 `data/journey/上月.md` 存在且五段结构完整 |
| 回放数据可信 | 档案中的 skills 新增数 vs `git log --since --until --diff-filter=A` 实测，±2 容差 |

## 5. 排障

| 症状 | 根因 | 处理 |
|------|------|------|
| waterlevel.log 无今日行 | daily-review 未跑或 skill 版本旧 | 查 cron last_status；确认加载 v4.0 skill |
| 字符数与实际差很大 | 用了 `wc -c`（字节数） | 改用 `len(open(...).read())` |
| 整理后条目缺失 | 误删（must_have 清单漏项） | 从 `.pre-consolidation` 快照恢复，补清单后重做 |
| 水位降不下来 | 措辞压缩空间枯竭 | 转向合并条目簇 + 删过期事实；检查是否高价值新增（无可整是合法状态） |
| journey 档案数据为空 | cron 未设 workdir | 更新 cron 加 `workdir`，手动补跑一次 |
| 提案从未出现 | 候选全被黑名单拦或写入判据过严 | 检查当日内容是否确无可固化事实；三个月判据是对的，不要放松 |
| 固化写入失败 | 注入层满（正是 7.5 该触发的场景） | 先跑一轮 7.5 整理再写入 |

---

## 6. 局限

- waterlevel.log 是明文日志，只记数字不含内容，但档案 `data/journey/*.md` 含个人里程碑——**此目录属个人数据，不进任何公开分发**（v4.0 发布管线已列为排除项）
- journey 的 todos 口径（「当月创建且已完成」）受 todos.json 无完成时间戳限制，统计精度有限，档案中需注明口径
- 整理动作由 cron 自主执行，依赖快照回滚兜底；快照只保留最近一次
